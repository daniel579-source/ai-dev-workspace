# ADR-0003：時間策略

- 日期：2026-10-15
- 狀態：已接受
- 確認者：repo owner（daniel579-source）
- 對應 ticket：Wayfinder「時間策略：時區、精度、同時間戳記與模組間先後」
- 相關決策：ADR-0002（LOG 以案件為單位在本機手動匯入）

## 背景

- LOG 時間戳記格式為 `yyyy-MM-dd HH:mm:ss.ffff`，精度 100 微秒，**沒有時區**（見 `docs/log-format-notes.md` 2.4 節）。
- 同一廠別的 EXE、PLC、Server 三個模組在**同一台電腦**上執行，共用同一個時鐘（ADR-0002）。
  - 2026-10-19 #47 補充：現場問卷確認各模組在同一台電腦、有自動對時、現場沒有時間對不上的經驗；容許誤差與 LOG 記錄的精度相同即可。第 3 點「系統不自動校正」的前提成立。
- 同一個命令在不同模組出現的時間差（中位數約 15～78 秒）是**處理流程**造成的，不是時鐘偏差（O-010）。
- 樣本中同時間戳記很常見（最高約 42%），同一檔案內時間會倒退（最多約 34 ms）（O-005、O-006）。
- 目前與預計的所有廠別都在**台灣**，沒有日光節約時間。
- 現場人員回報的時間（例如「10:05 掉貨」）可能和倉儲系統電腦的時鐘對不上。

## 決策

1. **時區**：廠別設定保留時區欄位，**預設為台北時間（UTC+8）**。第一階段**不處理日光節約時間**。畫面一律顯示廠別當地時間，並標明時區。
   - 2026-10-16 #19 補充：時區放在廠別設定的 `timeZone` 欄位，使用 IANA 或 Windows 的時區識別碼，預設 `Asia/Taipei`。LOG 不做時區換算，這個欄位只用來標明畫面顯示的是哪個時區；認不得的識別碼會註明「無法辨識」。
2. **時間值**：每筆事件保留**原始時間字串**，另存**標準化時間**，精度為 100 微秒、不捨入。
3. **系統不自動做模組之間的時鐘偏差校正**：預設照 LOG 記錄的時間呈現，系統不偵測、也不估計模組之間的偏差。用命令編號串連相關事件，屬於「回放的世界模型」的範圍。
   - 2026-10-16 #19 修改（使用者決定）：原為「模組之間不做時鐘偏差校正」。改為使用者可以為個別模組**手動**設定額外偏移量（第 5 點）；系統仍不代為判斷。
4. **時間解析失敗**：
   - 行首不是時間戳記的行：視為前一筆事件的延續（多行內容）。
   - 行首形似時間戳記但無法解析：保留為一筆事件，標示**時間無效**，排在前一筆有效事件之後。
5. **手動校正**：
   - 案件可以設定**一個整體偏移量**，套用到案件內所有天、所有模組，預設為 0。
   - 每次設定都記錄修改人（作業系統帳號）、修改時間與數值；畫面標示**已校正**；隨時可以改回 0。
   - 校正前的時間一律保留，校正只影響顯示與查詢用的時間。
   - **不支援分段校正**（同一案件內不同時段套用不同偏移量）。
   - 2026-10-16 #19 修改：除了整體偏移量，**每個模組可以另外設定額外偏移量**。某模組套用的偏移量＝整體＋該模組。單位是秒，精度 100 微秒，上限正負一天。某模組的偏移量不為 0 時，該模組的事件標示「已校正」，畫面頂端也顯示偏移量。排序依校正後的時間（ADR-0004 第 5 點）。仍然不支援分段校正。
6. **不確定性標示**：系統要能標示四種情況：
   - **同時間戳記**：多筆事件時間完全相同。
   - **時間倒退**：同一檔案中，這一筆比上一筆時間早。
   - **時間無效**：時間戳記無法解析。
   - **已校正**：案件的偏移量不為 0。（2026-10-16 #19 修改：事件所屬模組套用的偏移量不為 0。）

   如何呈現由「回放畫面與操作」決定；排序規則由「事件模型與排序規則」決定。

## 理由

- 工程師與現場溝通時都使用當地時間；顯示當地時間最不容易誤會。
- 所有廠別都在台灣，處理日光節約時間只會增加複雜度而沒有收益；保留時區欄位，日後出現海外廠別時不必改資料結構。
- 保留原始時間字串，才能追溯與稽核（NFR-009）；精度不捨入，才不會抹掉同一毫秒內的先後。
- 三個模組共用同一個時鐘，LOG 記錄的時間就是當時的真實先後；做校正反而會失真。
- 解析失敗不丟棄，符合 FR-012。
- 整體偏移量能以很低的成本解決「LOG 時間和現場時間對不上」的問題，同時保留校正前的時間，符合 FR-014。
- 模組偏移量（2026-10-16 #19）：給使用者判斷某個模組的時鐘不準時使用；由使用者手動設定，系統不代為判斷。

## 考慮過的替代方案與捨棄原因

| 方案 | 捨棄原因 |
|---|---|
| 模組之間**自動**做時鐘偏差偵測與校正（例如以命令編號的時間差估計） | 三個模組共用同一個時鐘；命令的時間差是處理流程造成的，校正會扭曲真實先後 |
| 一律以 UTC 顯示 | 和現場溝通時容易換算錯誤；所有廠別都在同一時區，沒有統一換算的需求 |
| 標準化時間只保留到毫秒 | 會把同一毫秒內的先後抹掉，增加同時間戳記的比例 |
| 時間無效的行直接丟棄或併入前一筆 | 違反 FR-012；可能藏有關鍵資訊 |
| 支援分段校正 | 目前沒有實例；一個整體偏移量已涵蓋大多數情況 |
| 不提供手動校正 | 無法處理倉儲系統電腦時鐘本身不準的情況 |

## 尚存風險

| 風險 | 影響 | 緩解方式 |
|---|---|---|
| 日後出現位於日光節約時間地區的廠別 | 時鐘撥回時同一小時出現兩次，排序與顯示錯誤 | 時區欄位已保留；屆時以新的 ADR 處理 |
| 模組偏移量會改變跨模組的先後（2026-10-16 #19） | 設錯時會誤導判讀 | 事件標示「已校正」、畫面頂端顯示偏移量、寫入稽核紀錄、隨時可以改回 0 |
| 需要模組偏移量的實際情境**待確認**（例如某些模組是否其實不在同一台電腦） | 背景中「三個模組共用同一個時鐘」的前提可能不成立 | 向現場確認各模組所在的電腦與對時方式；確認後更新背景。→ 2026-10-19 #47 問卷確認：同一台電腦、有自動對時，前提成立；模組偏移量保留給例外情況 |
| 倉儲系統電腦在案件期間被對時 | 單一偏移量無法同時修正前後兩段 | 已記入地圖的「Not yet specified」（分段時間校正） |
| 其他廠別的時間戳記格式不同 | 解析失敗比例升高 | 時間格式放在廠別設定中，可以調整；解析失敗的事件會被標示而不會遺失 |

## 後續驗證方式

- 以樣本確認：全部時間戳記都能解析；同時間戳記與時間倒退的筆數，與 `docs/log-format-notes.md` 的統計一致。→ 2026-10-18 以真實樣本**通過**（#47，`validation/results/real-sample-47-dev-pc.md`）：無效時間 0 筆；時間倒退 PLCLOG 6 處、WebServiceLOG 2 處；檔案內相鄰同時間的比例 PLCLOG 30%、EXEDebug 42%、BCR_LOG 20%。
- 人工製作含無效時間戳記的測試檔（虛構資料），確認標示與位置正確。
- 設定偏移量後確認：顯示時間改變、原始時間不變、改回 0 後完全恢復。
