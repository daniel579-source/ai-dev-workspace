# ADR-0004：事件模型與排序規則

- 日期：2026-10-15
- 狀態：已接受
- 確認者：repo owner（daniel579-source）
- 對應 ticket：Wayfinder「事件模型與排序規則」
- 相關決策：ADR-0002（以案件為單位匯入）、ADR-0003（時間策略）

## 背景

- 13 種 LOG 共用一種容器格式 `時間 | 等級 | Logger | 訊息`，有多行內容，每筆紀錄後有空行（`docs/log-format-notes.md` O-001、O-003）。
- 編碼 UTF-8 與 Big5 混用，沒有 BOM（O-002）。
- 同時間戳記很常見（最高約 42%）；同一檔案內時間會倒退，最多約 34 ms（O-005、O-006）。
- 同一 Logger 會因輪替分成封存檔與現行檔（O-007）。
- 重新匯入時，若舊檔是新檔的開頭，以新檔取代且行號不變（ADR-0002）。
- 時間無效的事件要排在前一筆有效事件之後（ADR-0003）。
- 需求：可追溯到原始檔案與行號（FR-040、NFR-007）、無法解析的內容不得丟棄（FR-012）、多行事件（FR-013）、穩定的排序（FR-026、NFR-008）、新增 LOG 種類不需大改（NFR-016）。

## 決策

### 1. 事件的邊界

一筆**事件**＝一行以時間戳記開頭的行，加上其後所有不以時間戳記開頭的行（延續行），直到下一個時間戳記為止。紀錄之間的空行與行尾空白不算進事件內容，原始檔照樣保留。事件記錄它在原始檔中的**起始行與結束行**。

### 2. 識別與定位

- 事件以「**模組、日期資料夾、檔案相對路徑、起始行號**」識別。
- 同時記錄**行號**（給人看）與**位元組位移**（讓系統快速讀回原文）。

### 3. 輪替檔案

同一 Logger 的封存檔與現行檔視為**一條連續的紀錄**：封存檔在前、現行檔在後。行號依實體檔案各自計算，追溯時指出實際的檔案。

### 4. 兩層欄位

- **基本欄位**（所有事件都有，匯入時產生）：標準化時間、原始時間字串、等級、Logger、模組、訊息全文、原始位置（檔案、起訖行、位元組位移）、旗標。
- **旗標**：時間倒退、同時間戳記、時間無效（含「時間為沿用」）、未知種類、編碼錯誤。
- **解析欄位**（依 Logger 種類而不同）：例如站點、設備、命令編號、ON／OFF 狀態。抽取規則放在**廠別設定**中，可依廠別調整。需要哪些解析欄位，由「回放的世界模型」決定。

### 5. 排序

1. 所有模組混在一起，**完全依標準化時間排序**。在原始檔中時間倒退的事件，標示「時間倒退」；原始行序可以在原始 LOG 檢視中看到。
2. 標準化時間完全相同時：
   - 同一檔案內：依原始行號（輪替檔依第 3 點的接續順序）。
   - 不同檔案之間：依**模組的固定順序**，再依 Logger 名稱。模組順序放在廠別設定中，預設 EXE → PLC → Server。
   - 這個先後只為了讓排序穩定、可重現，**不代表因果**；畫面標示「同時間戳記」。
3. 時間無效的事件**沿用同一檔案中前一筆有效事件的標準化時間**，並標示「時間為沿用」，再依行號排在那一筆之後。
4. 案件的手動偏移量（ADR-0003）對所有事件加上同一個常數，不改變排序。
5. **搜尋結果採用相同的排序規則。**

### 6. 異常內容

- **無法解碼的位元組**：保留原始位元組，畫面用替代字元顯示，標示「編碼錯誤」；事件不丟棄。
- **整個檔案無法解析**（不符合共通格式）：不產生事件、不進時間軸，列在案件的檔案清單中並標示「無法解析」，可以用原始文字的方式開啟。

## 理由

- 以行首時間戳記切分事件，對 13 種 LOG 都適用，不需要逐一設定。
- 本系統以時間為核心，時間軸單調遞增最直覺；倒退只有數十毫秒且有標示，原始順序也沒有遺失。
- 同時間戳記的真實先後無法從 LOG 得知，只能保證排序一致並如實標示，避免讓使用者誤以為有因果。
- 行號加位元組位移兼顧可讀性與讀回原文的效率；加上 ADR-0002 的「開頭相符就取代、行號不變」，識別碼在重新匯入後仍然穩定。
- 共通的基本欄位與依種類而異的解析欄位分開，新增 LOG 種類只需要新增規則（NFR-016）。

## 考慮過的替代方案與捨棄原因

| 方案 | 捨棄原因 |
|---|---|
| 保留檔案內的原始順序，只在檔案之間依時間合併 | 時間軸會出現時間不單調的情況，不直覺；原始順序仍可在原始 LOG 檢視中看到 |
| 每一行都當作一筆事件 | stack trace、SQL、HTTP 內容會被拆散，難以閱讀與搜尋 |
| 同時間戳記時不定義先後 | 每次查詢的順序可能不同，違反 NFR-008 |
| 以流水號識別事件 | 重新匯入後流水號會改變，已有的追溯與書籤會失效 |
| 解析欄位寫死在程式中 | 不同廠別的 LOG 差異需要改程式，違反 NFR-016 |
| 無法解析的檔案以「整個檔案一筆事件」放進時間軸 | 沒有可信的時間，放進時間軸會誤導 |

## 尚存風險

| 風險 | 影響 | 緩解方式 |
|---|---|---|
| 其他廠別的 LOG 中，延續行也以類似時間戳記的文字開頭 | 事件被錯誤切分 | 時間戳記的判定格式放在廠別設定中，必要時加嚴（例如要求後面接 ` \| 等級 \| `） |
| 預設的模組順序被誤認為因果 | 錯誤推論事件先後 | 畫面明確標示「同時間戳記」；說明文件寫明此順序沒有因果意義 |
| 檔案很大時，位元組位移與行號的對應計算成本高 | 匯入變慢 | 在「儲存與索引候選方案比較」中評估 |

## 後續驗證方式

- 以樣本確認：事件數與 `docs/log-format-notes.md` 統計一致（例如 PLCLOG 6,532 筆、DBLOG 35 筆且每筆含 stack trace）。
- 確認時間倒退的事件筆數與統計一致（PLCLOG 6 處、WebServiceLOG 2 處），且都有標示。
- 同一查詢重複執行，順序完全相同。
- 模擬重新匯入「新檔多出後半段」後，原有事件的識別碼不變。

## 影響範圍

- **回放的世界模型**：決定需要哪些解析欄位；以命令編號串連事件。
- **回放畫面與操作**：呈現旗標；提供混合檢視（以顏色區分模組）與分軌檢視。
- **儲存與索引候選方案比較**：支援事件識別方式、依時間排序的讀取、關鍵字搜尋。
- **搜尋模式與比對規則**：搜尋結果沿用本 ADR 的排序規則。
