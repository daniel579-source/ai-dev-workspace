# ADR-0005：回放的世界模型

- 日期：2026-10-15
- 狀態：已接受
- 確認者：repo owner（daniel579-source）
- 對應 ticket：Wayfinder「回放的世界模型：站點、設備、貨物的狀態推導」
- 相關決策：ADR-0002（廠別設定）、ADR-0003（時間策略）、ADR-0004（事件模型與排序規則）

## 背景

- 回放的目標是依 LOG 在 Layout 上重現站點、設備與貨物的狀態變化；第一階段為站點層級（GLOSSARY「回放」）。
- 以樣本 LOG 追蹤命令的結果（只在本機分析，以下為去識別化描述）：
  - 一個命令有清楚的生命週期：EXE 建立任務 → Server 分段指派給搬送機（每段有目的地）→ 搬送機回報抵達 → EXE 回報完成。一個出庫命令會經過兩段以上、由不同搬送機執行。
  - PLC 的站點紀錄帶有命令編號（例如寫入命令資料、卸貨完成），也記錄站點訊號位元的 ON／OFF（在席、取物可、置物可、定位、夾臂等）。
  - 入庫時，入庫站點以條碼讀到**棧板編號**，接著逐一讀到棧板上每個**桶的條碼**（樣本中多為 4 桶），並寫入同時帶有命令編號與棧板編號的紀錄。棧板編號在三個模組都看得到。
  - 位置編號有三套：7 位數（儲位）、4 位數（WCS 的站點）、`A-nn`（PLC 的站點）。
  - 樣本中有站點模式代號的紀錄（`ModeChangeREQ`，值為 0、1、2）、派取貨命令時的 `Status=AUTO`，以及帶有發生時間與復歸時間的警報紀錄。樣本中**沒有** ON-LINE／OFF-LINE 的紀錄。
- 使用者確認的事實：
  - `SRCA`、`SSCA`、`STVT` 都是**搬送機**；`EQxxx` 是**其他公司的對接設備**。
  - 命令類型：S＝入庫、R＝出庫、P＝搬送。其中 SSCA、STVT 與 P 的定義是**暫訂**。
  - 7 位數編號是儲位（排、列、層）。
  - 一個棧板上可能有數量不定的桶，各有編號。
  - `ModeChangeREQ` 是工作站（站點）的模式代號。
  - 搬送機的 ON-LINE／OFF-LINE 只有在切換時才會留下紀錄。
- 使用者希望未來的 Layout 走 3D 風格（以一個本機的 3D 示意頁為參考，不放進 repo）。

## 決策

### 1. 世界的組成

| 元素 | 說明 |
|---|---|
| **站點** | 貨物停留或交接的位置。一個站點可以有**多個別名**（WCS 的 4 位數編號、PLC 的 `A-nn`），由使用者在 Layout 上手動對應。LOG 中出現但還沒對應的編號，集中在「未對應」區，不丟棄 |
| **搬送機** | 負責移動貨物的設備（`SRCA`、`SSCA`、`STVT`） |
| **對接設備** | 其他公司的設備（`EQxxx`），貨物在這裡交出 |
| **電梯** | 在樓層之間搬送貨物的設備；和搬送機是不同的種類，有自己的 LOG（2026-11-06 #102 補充，見第 11 點） |
| **儲位** | 料架上的存放格，以 7 位數編號表示排、列、層；世界模型**逐格記錄** |
| **貨物** | 以**棧板**為移動單位，附帶數量不定的**桶編號清單**；桶不會單獨移動，桶清單有變動時只標示變動 |
| **命令** | 一趟搬送任務，分成多段，每段由一台搬送機執行；類型 S＝入庫、R＝出庫、P＝搬送 |

兩套站點編號的正式對照表**待確認**；日後有對照表時，改成匯入。

2026-10-19 #47 補充：現場問卷確認**沒有對照表**，兩套編號是**一對一**。兩個編號都設為同一個站點的別名（ADR-0006 第 2 點），不提供對照表匯入。

### 2. 貨物的位置

- **只由命令決定**：
  - 某一段派給搬送機時，貨物在「搬送機上」。
  - 收到抵達回報時，貨物在該段的目的地（站點或儲位）。
- **出現**：入庫站點讀到棧板條碼時，或 LOG 第一次提到這個棧板時（例如出庫命令的來源儲位，表示它在案件開始前就已經在那裡）。
- **消失**：交給對接設備並收到完成回報時，標示「已交出」並從畫面上移除；之後如果又被命令提到，再讓它出現。
- **在儲位中**：入庫命令抵達儲位後，貨物留在該儲位，直到出庫命令把它取走。
- 2026-11-04 #47 補充（使用者決定）：**儲位一律以 LOG 記載的內容為準**，依載入的 LOG 照時間變化：
  - 還沒執行到與該儲位有關的 LOG 時，儲位是「**未取得資訊**」。
  - 執行到與該儲位有關的 LOG 時，以 LOG 記載的內容為準（有哪個棧板，或已經空了），直到 LOG 再出現該儲位的變化。
  - 儲位因此有三種狀態：未取得資訊、有貨（棧板）、空（LOG 記載已取出）。「空」與「未取得資訊」在畫面上要能區分。
  - 「LOG 記載」包含下列情況：
    - 放進儲位：派送紀錄寫明目的地是儲位，加上該段的作業完成（或抵達）紀錄，視為 LOG 記載該儲位放入這個棧板。
    - 從儲位取出：派送紀錄寫明來源是儲位，視為 LOG 記載該儲位在派送時有這個棧板；搬送機取走後該儲位變成「空」。
  - 理由：樣本中沒有單獨記錄「放入哪個儲位」的紀錄（只有派送的目的地與作業完成），不採用就無法顯示任何儲位；放入與取出都有 LOG 依據，不是推測。
  - 捨棄的方案：只採用同一筆紀錄中明確寫出儲位與棧板的紀錄（樣本中沒有這種紀錄，儲位會一直是未取得資訊）；儲位一開始視為空（沒有 LOG 依據，違反第 7 點）。
  - 風險：派送後實際放入的儲位與派送目的地不同（例如改派儲位）時，回放會顯示派送的目的地；取消與改派的 LOG 樣式仍待確認，確認後再調整。
  - 已實作（#95，2026-11-05）。實作時補充的細節（使用者裁決或 Jev 判斷）：
    - 抵達儲位與派送目的地是儲位的作業完成，都把命令的棧板放進儲位；棧板之前沒有位置紀錄時也建立（使用者裁決）。目的地不是儲位時，作業完成仍不推導位置（#53）。
    - 派送來源是儲位、但這個棧板之前沒有位置紀錄時，建立棧板並標示「案件開始前就在」該儲位，接著移到搬送機上（使用者裁決）。
    - 派送來源是儲位、命令沒有棧板編號時，該儲位仍變成「空」（Jev，信心度 0.72）。
    - 儲位記錄著另一個棧板時，以新的 LOG 為準：儲位改為新的狀態，原本那個棧板的位置改為不明，不推測它去了哪裡（Jev，信心度 0.68）。
    - 料架側視圖的棧板欄顯示棧板編號、「空」或「—」（未取得資訊），造成它的事件可以點選跳過去；料架摘要也列出空的儲位數。

### 3. 站點的狀態

- **在席指示燈**：顯示在站點右上角，ON 亮、OFF 暗、未知是灰色。在席位元**不改變**貨物的位置。
- **不一致提示**：命令與在席訊號矛盾時（例如命令說貨物已抵達某站點，但該站點的在席一直是 OFF），在站點上加提示，**不改變**貨物的位置，也不由系統判斷哪一邊才對。
- **站點模式**：顯示 `ModeChangeREQ` 的代號；代號的名稱在廠別設定中填寫，沒填時直接顯示代號。0、1、2 的意義**待確認**。
  - 2026-10-19 #47 補充：0、1、2 的意義已由現場問卷確認，名稱填在本機的廠別設定（真實的代號意義不進 repo）。PLC 的 LOG 中另有兩個站點欄位，分別記錄自動／手動模式，以及手動模式下的入庫／出庫；代號意義已取得，但本機樣本中沒有出現（樣本為作業較少的一天），解析規則**待有出現的樣本**再寫。
    2026-10-19 #70 補充：樣本中的站點狀態變化有自動、手動、異常的文字值，以下方的「運轉狀態」處理；另一個欄位（手動模式下的入庫／出庫）仍待樣本。
  - 2026-10-19 #58 補充：廠別設定有名稱時，回放（站點詳細資訊、設備狀態表）只顯示名稱，沒有時顯示代號；設備狀態表在模式未知時不顯示模式。造成狀態的事件不變，仍可追溯到原始 LOG（設定欄位見 ADR-0006 第 7 點）。
- **運轉狀態**（2026-10-19 #70 補充）：PLC 在站點切換時記錄的文字值，例如自動、手動、異常（範例）。
  - 和站點模式分開；照 LOG 的文字顯示，不限定種類；第一次切換之前為「未知」。
  - 顯示在站點的詳細資訊與設備狀態表，附造成它的事件。
  - 值為「異常」時只顯示狀態，「異常中」標示仍只由警報的發生／復歸決定（第 5 點）。
  - Layout 回放畫面上，運轉狀態已知且不是「自動」（以文字比對）時，站點圖示顯示小標記（運轉狀態的第一個字），不用點開就看得到。
- **異常**：依第 5 點。
- **其他訊號**（取物可、置物可、定位、夾臂、入庫要求等）：點開站點時以清單顯示 ON／OFF，不改變站點的顏色。

### 4. 搬送機的狀態

三層，彼此獨立：

| 層 | 值 |
|---|---|
| 連線 | ON-LINE、OFF-LINE、未知（只有切換時才有紀錄，第一次切換之前都是未知） |
| 模式（只在 ON-LINE 時有意義） | 自動、手動、未知 |
| 作業 | 閒置，或執行中（顯示命令編號與目的地） |

另外，有未復歸的警報時標示**異常**。搬送機在 Layout 上是固定位置的圖示，不移動。哪一行 LOG 代表哪一種狀態，在廠別設定中定義。

- 2026-11-06 #101 修改：有指定導軌的搬送機，回放時沿導軌移動，位置為推估（見第 10 點）。沒有指定導軌的搬送機仍固定不動。

### 5. 異常

- 某台搬送機或某個站點，從警報發生到警報復歸，標示為「異常中」。
  - 2026-11-06 #102 補充：電梯也可以是警報的對象（第 11 點）。
- 案件範圍內只有發生、沒有復歸時，一直標示到案件結束，並註明「未見復歸紀錄」。
- 異常熱區的判定不在本 ADR 範圍。

### 6. 命令的狀態

- 已建立 → 第 N 段執行中（搬送機、目的地）→ 第 N 段已抵達 → 已完成；另有異常／中斷。
- 到案件結束時還沒完成的命令，標示「**案件範圍內未完成**」，不推測後續發展。
- 命令可以查詢，並列出它以命令編號串起來的所有跨模組事件。
- 命令被取消或改派時的 LOG 樣式**待確認**（樣本中沒有看到）。
- 2026-10-18 #53 補充：新增狀態「**第 N 段作業完成（地點未記錄）**」（`segmentFinished` 效果）。不推導地點，也不沿用派送時的目的地；貨物位置維持最後的紀錄；執行這一段的搬送機回到閒置；不算命令完成。理由：使用者決定不推導地點（2026-10-18）。捨棄的方案：沿用派送目的地（推導出的地點會和 LOG 實際寫的混在一起）；讓 `segmentArrived` 不需要目的地（寫錯的規則不會被擋下）。
  - 2026-11-04 #47 修改（使用者決定）：**派送的目的地是儲位時**，作業完成視為放入該儲位（見第 2 點的補充）；目的地是站點或其他位置時維持上述規則，不推導地點。

2026-10-16 #26 補充：

- 取消：效果 `commandCancelled`（需要命令編號）把命令改為「已取消」，執行中的搬送機回到閒置；貨物位置不推測，維持最後的紀錄。已取消的命令不算「案件範圍內未完成」。
- 改派：同一段再派給另一台搬送機時，命令改跟新的那台；原本那台的作業不推測，維持最後的紀錄。
- 取消與改派的 LOG 樣式仍**待確認**，不提供初始規則，由廠別設定填寫；以上處理只以虛構資料驗證。「異常／中斷」要等到有樣本再定義，目前沒有實作。

### 7. 初始狀態

- 回放開始時，所有站點、搬送機、儲位都是「**未知**」（灰色），不假裝是空的。
- 第一次在 LOG 中確定狀態後，才改成已知的狀態。
- 2026-11-04 #47 補充：儲位的「未知」稱為「未取得資訊」；LOG 記載已取出的儲位是「空」，與未取得資訊分開顯示（見第 2 點）。

### 8. 解析欄位

回放需要從事件中抽取下列解析欄位（ADR-0004），抽取規則放在廠別設定中，實際規則在實作規格階段依 `docs/log-format-notes.md` 訂定：

- 站點編號（WCS 4 位數、PLC `A-nn`）、搬送機編號、對接設備編號、儲位
- 命令編號、命令類型、來源、目的地
- 棧板編號、桶編號
- 訊號名稱與 ON／OFF、站點模式代號、站點運轉狀態（2026-10-19 #70 補充）
- 警報的發生或復歸、警報代碼
- 連線狀態、自動或手動

實作方式（2026-10-16 #23 補充）：

- **規則的形式**：每條規則有名稱、模組（可省略）、Logger（可省略）、正規表示式。具名群組的名稱就是欄位：`station`、`vehicle`、`dock`、`storage`、`command`、`commandType`、`source`、`destination`、`pallet`、`bin`、`signal`、`signalValue`、`stationMode`、`alarm`、`alarmCode`、`online`、`mode`。
- 一筆事件中每個符合處都會抽出；同一事件內，相同的種類與值只記一次。
- **初始規則**只涵蓋樣本中看過的格式（`docs/log-format-notes.md` 第 3、4 節）：命令編號、站點與設備、站點狀態變化（訊號 ON／OFF）、棧板命令、設備編號。警報、連線、自動／手動、儲位、桶、命令類型等格式**待確認**，不提供初始規則，由廠別設定填寫。
- 單一訊息比對超過 200 毫秒時略過那一筆，不中斷匯入。

效果與推導（2026-10-16 #24 補充）：

- **效果**：規則可以宣告「效果」，代表這一行 LOG 是哪一種狀態變化，參數就是規則抽出的欄位。共 10 種（#53 後為 11 種，見下方補充）：`signal`、`stationMode`、`palletRead`、`commandCreated`、`segmentDispatched`、`segmentArrived`、`commandCompleted`、`connection`、`alarmRaised`、`alarmCleared`。每種效果有必要的欄位，存檔前檢查。
- 新增欄位 `segment`（第幾段）。重複的群組可以抽出多個值（例如一行中的多個桶）。
- **在席訊號**：`signal` 效果的訊號名稱等於廠別設定的在席訊號時，決定在席燈；預設為「在席」（樣本中看過）。
- **初始規則**只有「站點狀態變化」帶效果（`signal`）；命令、派送、抵達、警報、連線等效果的 LOG 格式**待確認**，由廠別設定填寫。
- 2026-11-06 #102 補充：新增欄位 `elevator`（電梯編號），以及電梯的三種效果 `elevatorDispatched`、`elevatorArrived`、`elevatorFinished`（第 11 點）；警報效果的對象可以是電梯。LOG 樣式**待確認**。
- 2026-10-19 #70 補充：新增欄位 `stationStatus`（運轉狀態）與效果 `stationStatus`（站點運轉狀態，必要欄位為站點與運轉狀態），效果增加為 12 種。
- 2026-10-18 #53 補充：效果增加為 11 種，新增 `segmentFinished`（命令的一段作業完成，但 LOG 沒有記錄地點；必要欄位只有命令編號）。真實樣本中，放進儲位或從儲位取貨的那一段只有「作業完成回報」，沒有地點。不放寬 `segmentArrived` 的必要欄位，是為了讓漏抓目的地的抵達規則在存檔時仍被擋下。
- **推導細節**：
  - LOG 中的編號以別名對應到元素；符合儲位規則（ADR-0006 第 4 點）的編號視為儲位；其他的位置不明。
  - 對應不到 Layout 的編號不產生元素狀態。
  - 命令沒有「建立」的紀錄就先出現派送時，仍會建立命令（類型等欄位為未知）。
  - 「完成回報」不會把「已交出」改成一般的「已完成」。
  - 每個狀態值都記錄造成它的事件序號。

### 9. 畫面方向

- 第一階段做 **2D 俯視**的站點層級回放。
- Layout 保留 3D 需要的資訊（例如儲位的排、列、層，以及元素的高度），之後可以升級成 3D。
- 3D 畫面與連續移動動畫不在第一階段範圍。
  - 2026-11-06 #101 修改：使用者決定第一階段加入「搬送機沿導軌移動」，位置一律標為推估（第 10 點）。3D 畫面仍不在範圍內。

### 10. 搬送機沿導軌移動（2026-11-06 #101 補充）

樣本 LOG 中沒有搬送機的實際位置或座標，只有命令的一段派送（含目的地，可能有來源）與抵達、作業完成（2026-11-06 本機檢查，只看關鍵字次數）。使用者決定依時間內插，並一律標為推估。

- **範圍**：只影響有指定導軌的搬送機（ADR-0006 第 14 點）。沒有指定導軌的搬送機維持固定位置（Jev，0.76）。
- **位置與依據**：
  - **第一次派送之前**：畫在 Layout 上放的位置，標為「位置未取得資訊」（Jev，0.77）。
  - **派送到抵達之間**：依經過時間的比例，畫在導軌上起點與終點之間，標為**推估**。
    - 起點：優先用派送紀錄的來源；沒有來源時，用搬送機上一個位置；兩者都沒有時不內插，直接畫在終點並標為推估（Jev，0.14，使用者確認）。來源和上一個位置不同時，搬送機在派送的那一刻跳到來源。
    - 終點：派送的目的地，一律投影到導軌上最近的點，不設距離上限（Jev，0.26 偏向不設，使用者確認）。
      - 站點、對接設備：元素的中心。
      - 儲位：依儲位規則拆出排、列，取那一排料架上那一列的中心，層不影響（Jev，1.0）。
    - 閉合的導軌：依點的順序方向前進（第 1 點 → 第 2 點 → …）（Jev，0.49，使用者確認）。實際的行進方向**待確認**（`docs/log-format-notes.md` O-018）。
  - **抵達之後**：畫在終點，標為「依 LOG：已抵達（位置為目的地在導軌上的投影）」（Jev，0.88）。
  - **沒有抵達**（到案件結束都沒抵達，或抵達前取消）：留在起點，標示「執行中，抵達時間未知」，不內插（Jev，0.06，使用者確認）。
  - **作業完成**（LOG 沒有地點）：不推導位置，停在起點，標示「作業完成，地點未記錄」，和 #53 一致（Jev，0.28，使用者確認）。
  - 維持 Layout 上設定的旋轉角度，只移動中心點（Jev，0.92）。
- **畫面**：
  - 推估的位置加虛線框，和防火門的推估相同（Jev 0.58，使用者決定）。
  - 詳細資訊列出位置的依據（推估、依 LOG、未取得資訊）與派送、抵達的事件，可以跳過去。
  - 播放時目前時刻連續前進，搬送機也跟著連續移動。
- **實作**：Engine 新增一個類別，輸入效果、Layout 與每筆事件的時間，算出任一時刻的位置與依據，可以單元測試；電梯（#102）日後可以沿用（Jev，0.76）。

### 11. 電梯的狀態（2026-11-06 #102 補充）

自動化倉儲可能分布在不同樓層，電梯在樓層之間搬送貨物。使用者說明：日後 LOG 中會有「電梯從 A 站點到 B 站點」的命令紀錄，但搬送機有不同的 LOG，所以電梯是獨立的種類（ADR-0006 第 15 點）。目前沒有電梯的 LOG 樣本，樣式**待確認**（`docs/log-format-notes.md` O-019）。

- **解析**（Jev，0.96）：
  - 新增欄位 `elevator`（電梯編號），以別名對應到電梯元素。未對應的編號也列入「未對應」。
  - 新增三種效果，不沿用搬送機的欄位與效果：
    - `elevatorDispatched`（派給電梯）：命令、電梯、目的地；來源可選。
    - `elevatorArrived`（電梯抵達）：命令、目的地。
    - `elevatorFinished`（電梯作業完成）：命令。
  - 警報效果的對象加上電梯（異常中）。連線、自動手動先不做，等有 LOG 樣本（Jev，0.42，使用者確認）。
- **狀態**：電梯有自己的狀態，不放在搬送機的狀態中：作業（未知、閒置、執行中）、命令、目的地、目前樓層、出發樓層、前往樓層，每一項都記錄造成它的事件。
- **目前樓層**：
  - 第一次事件前：未取得資訊。
  - 派送時：
    - 出發樓層取目前樓層；目前樓層未知時，依來源站點的樓層推估（使用者決定）。
    - 前往樓層取目的地站點的樓層。
  - 移動中：顯示「移動中：1F → 2F」並標為推估；目前樓層維持出發樓層（Jev，0.74）。
  - 抵達：目前樓層取抵達站點的樓層（依 LOG）。
  - 作業完成（LOG 沒有地點）或取消：停在出發樓層，標示依據。
- **貨物**：新增位置種類「在電梯上」。派給電梯時貨物上電梯；抵達時貨物到目的地（和搬送機相同的規則）。電梯在每一層的圖示都顯示載著的棧板（Jev，0.14，使用者確認）。
- **命令**：命令的一段由電梯執行時，命令狀態照常更新，「執行者」顯示電梯的名稱。
- **回放**：
  - 每一層的電梯圖示都顯示執行中或閒置、載著的棧板、目前樓層，移動中時顯示「1F → 2F」。
  - 設備狀態表列出電梯，「樓層」欄顯示目前樓層。
  - 開啟「跟隨切換樓層」時，選取電梯切到它目前所在的樓層；未知時不切換（使用者決定）。

## 理由

- 命令有完整的生命週期，而且帶有棧板編號，是唯一能回答「哪一個貨物、在哪裡」的依據；在席位元只知道「有沒有東西」，不知道是哪一個。
- 在席位元獨立顯示，加上不一致提示，讓工程師一眼看出「系統以為」與「感測器看到」的差異，這正是除錯需要的線索，而系統不必猜測。
- 「未知」和「空的」在除錯時意義不同；樣本只涵蓋部分時間，初始狀態無法從 LOG 得知。
- 站點別名由使用者手動對應，對應錯誤時只要改 Layout，不必重新匯入。
- 狀態的判定規則放在廠別設定，不同廠別的 LOG 差異不需要改程式（NFR-016）。
- 世界模型只記錄離散位置，不受畫面是 2D 或 3D 影響；先確保推導正確，再提升畫面。
- 電梯（2026-11-06 #102）：電梯有自己的 LOG（使用者），獨立的欄位與效果讓兩者的規則互不影響；狀態另外記錄，搬送機的推導不必處理樓層。目前樓層只有抵達時以 LOG 為準，其他時候都標示依據。
- 搬送機沿導軌移動（2026-11-06 #101）：看得到搬送機大概在哪裡、往哪裡去，比只看「執行中」更容易還原當時的情況（使用者）。LOG 沒有位置，所以移動中一律標為推估；抵達時以 LOG 為準，和推估分開。位置計算不放進世界模型，世界模型仍只記錄離散狀態。

## 考慮過的替代方案與捨棄原因

| 方案 | 捨棄原因 |
|---|---|
| 貨物位置只看站點感測（在席位元） | 不知道是哪一個貨物，也無法表示貨物在搬送機上或在儲位中 |
| 命令與在席並用，以在席決定實際到位時間 | 使用者選擇讓兩者獨立顯示；以不一致提示保留差異，畫面規則較單純 |
| 以桶為移動單位 | 桶不會單獨移動；以棧板為單位即可，桶清單作為附屬資訊 |
| 回放開始時把未知的元素當作空的 | 會誤導判斷，例如以為站點上沒有貨物 |
| 兩套站點編號由系統自動推測對應 | 沒有可靠依據；錯誤的對應會讓整個回放失真 |
| 第一階段就做 3D（含或不含連續移動） | 對用戶端技術要求高；連續移動是推測而非 LOG 記錄的事實；先確保狀態推導正確 |
| 搬送機只用單一狀態值（例如閒置／執行中／異常） | 連線、模式、作業彼此獨立，混成一個值會遺失資訊 |
| 搬送機只停在已知點，不內插（2026-11-06 #101） | 使用者選擇依時間內插，以推估標示 |
| 起點只用上一個位置（2026-11-06 #101） | 使用者確認優先用派送的來源，比較貼近 LOG 記載 |
| 閉合導軌走較短的那一邊，或每條導軌設定方向（2026-11-06 #101） | 實際方向待確認；先依點的順序，必要時再加設定 |
| 沒有抵達時以案件結束當作抵達時間來內插（2026-11-06 #101） | 會畫出 LOG 沒有支持的移動 |
| 作業完成時以派送的目的地當作抵達處（2026-11-06 #101） | 和 #53「LOG 沒有地點就不推導」的原則不一致 |
| 目的地離導軌太遠時不內插（2026-11-06 #101） | 使用者確認一律投影到最近的點 |
| 電梯沿用搬送機的欄位與效果（2026-11-06 #102） | 使用者說明搬送機有不同的 LOG |
| 只在電梯目前所在樓層顯示棧板（2026-11-06 #102） | 使用者確認每層都顯示 |
| 移動中時目前樓層為未知（2026-11-06 #102） | 看不出從哪一層出發（Jev） |
| 第一次抵達前不從來源推斷樓層（2026-11-06 #102） | 使用者決定依來源站點推估，並標示依據 |
| 電梯的連線、自動手動第一版就做（2026-11-06 #102） | 沒有樣本，欄位與值都不知道 |

## 尚存風險

| 風險 | 影響 | 緩解方式 |
|---|---|---|
| SSCA、STVT 與命令類型 P 的定義是暫訂 | 分段與狀態推導規則要調整 | 設備種類與命令類型的對應放在廠別設定中 |
| 兩套站點編號沒有對照表 | 手動對應費時且可能出錯 | 「未對應」區讓遺漏一目了然；日後改為匯入對照表。→ 2026-10-19 #47：現場沒有對照表、編號一對一，維持手動對應 |
| 站點模式代號的意義、取消或改派命令的樣式待確認 | 顯示代號而非名稱；命令狀態可能錯誤 | 已記入地圖 Not yet specified；取消與改派先以可設定的效果處理（#26），取得樣本後補充規則並確認推導方式 |
| 不同廠的站點運轉狀態文字不同（2026-10-19 #70） | 「不是自動」的判斷與標記可能不適用 | 照 LOG 文字顯示，不做對應；小標記只以「自動」的文字比對，其他廠若用不同文字再調整 |
| ON-LINE／OFF-LINE 只在切換時記錄 | 多數時間連線狀態為未知 | 如實顯示未知；不推測 |
| 案件範圍外的事件（例如前一天入庫）無法得知 | 貨物的桶清單或來源不完整 | 案件可以包含多天（ADR-0002）；不完整時標示未知 |
| 真實樣本的「命令結束」以刪除命令的紀錄判斷（2026-10-18） | 命令被取消時若也刪除，會被當成完成 | 取消的 LOG 樣式**待確認**；確認後調整本機廠別設定的規則 |
| 真實樣本的規則沒有抓棧板（2026-10-18） | 回放不追蹤棧板位置 | 棧板編號在建立命令的 SQL 中位置固定但不易可靠擷取；之後再補規則。→ 2026-11-04 #47：已在本機廠別設定補上規則（依欄位位置取值，40 個命令都取得到，34 個與入庫紀錄相同）；出庫棧板因建立命令不抓來源而不出現，待儲位實作後再確認 |
| 搬送機的速度、中途停留、繞路都沒有 LOG（2026-11-06 #101） | 移動中的位置可能和實際不同 | 一律標為推估（虛線框）；抵達以 LOG 為準 |
| 起點用派送的來源（2026-11-06 #101） | 來源和上一個位置不同時，畫面上會瞬間移動 | 詳細資訊列出依據的事件 |
| 閉合導軌的行進方向待確認（2026-11-06 #101） | 依點的順序可能和現場方向相反，移動路線畫錯邊 | 建 Layout 時依現場方向畫點；取得資訊後再確認（O-018） |
| 目的地離導軌很遠（2026-11-06 #101） | 投影的位置沒有意義 | 建 Layout 時把導軌畫在設備旁 |
| 電梯的 LOG 樣式未知（2026-11-06 #102） | 效果的必要欄位可能要調整 | 取得樣本後檢查（O-019、S-012） |
| 依來源推估的出發樓層（2026-11-06 #102） | 可能不正確 | 標為推估；第一次抵達後以 LOG 為準 |
| 輸送線上的移動沒有 LOG 紀錄（2026-11-04 #47） | 棧板讀到條碼後沿輸送線移動，回放仍留在讀條碼的站點，產生不一致提示（樣本 34 段） | 照原則不推導位置；不一致提示讓工程師看出差異；是否要以在席接力推導，待工程師確認後再討論 |

## 後續驗證方式

- 以樣本確認：每個命令的分段數、抵達回報與完成回報能正確串起；抵達回報筆數與命令數一致（樣本約 40 對 41）。→ 2026-10-18 以真實樣本**通過**（#47、#53，`validation/results/real-sample-47-dev-pc.md`）：規則只放在本機的廠別設定（含現場系統的內部名稱，不進 repo）。每一段都是「派送 → 抵達或作業完成」成對出現；39 個命令完成，1 個到當天結束仍在進行（標示案件範圍內未完成），1 個只被提到。抵達回報只出現在到站的那一段，放進儲位或從儲位取貨時是作業完成回報，因此是 40 對 41。
- 以樣本確認：入庫站點讀到的棧板與桶，能對應到同一命令的後續各段。→ 2026-11-04 棧板**通過**（#47，`validation/results/real-sample-47-dev-pc.md` 第 6 節）：每個命令 1 個棧板、1 個站點，每個棧板只屬於 1 個命令，派送後不會被拉回站點；桶尚未串起（桶清單的紀錄沒有棧板編號），**待確認**。
- 以樣本列出「不一致提示」出現的位置與次數，請使用者判斷是否合理。→ 2026-11-04 已列出（#47，同上第 7 節）：39 段，34 段為讀到條碼後沿輸送線移動，4 段為取貨點在席早於派送紀錄 OFF，1 段為抵達後又往下游移動。依使用者指示，每一段的命令 LOG 與相關設備 LOG 已分別列出並綜合分析，交給工程師確認（只在本機）；推測都是**假設**。
- 人工製作虛構資料，確認未知狀態、未見復歸紀錄、案件範圍內未完成的標示正確。
- 以虛構資料確認電梯：載貨從 1F 站點到 2F 站點，目前樓層、出發與前往樓層、貨物位置正確；第一次事件前為未取得資訊；作業完成與取消停在出發樓層（2026-11-06 #102）。
- 以虛構資料確認搬送機沿導軌移動：直線與環狀導軌、目的地為站點與儲位、沒有抵達、作業完成、取消；往前、往後移動與跳到任意時刻時，位置與依據相同（2026-11-06 #101）。

## 影響範圍

- **Layout 模型與設定檔**：站點別名與未對應區、儲位的排列層、保留 3D 資訊、在席指示燈的位置。

- **儲存與索引候選方案比較**：解析欄位的儲存、以命令編號與棧板編號串連事件。
