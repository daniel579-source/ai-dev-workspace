# ADR-0010：搜尋模式與比對規則

- 日期：2026-10-16
- 狀態：已接受
- 確認者：repo owner（daniel579-source）
- 對應 ticket：Wayfinder「搜尋模式與比對規則」
- 相關決策：ADR-0004（事件模型與排序規則）、ADR-0005（解析欄位）、ADR-0006（別名）、ADR-0008（回放畫面與操作）、ADR-0009（電話號碼遮罩）

## 背景

- 使用者需求：在設定的時間區間內輸入關鍵字，把所有符合的事件依時間排序列出（排序規則同 ADR-0004）。
- 相關需求：FR-020～FR-026、FR-040、NFR-002、NFR-017（不需要學習查詢語法）。
- LOG 的編碼是 UTF-8 與 Big5 混用；事件有多行的延續行（stack trace、SQL、HTTP 內容）（`docs/log-format-notes.md`）。
- 搜尋結果放進事件清單，與「目前時刻」連動（ADR-0008）；畫面上只遮罩電話號碼（ADR-0009）。
- 量級：樣本一天約 20 MB；實際量級**未知**。

## 決策

### 1. 比對規則

- 預設**不分大小寫**，**全形與半形視為相同**；提供「區分大小寫」選項。
- **部分比對**（訊息中含有該字串即符合）；不做中文斷詞。
- Big5 與 UTF-8 檔案**先解碼成文字再比對**；無法解碼的位元組不會符合任何關鍵字。
- 比對**整筆事件內容**，包含延續行；符合處在延續行時，標示「符合處在第 N 行」，展開後以醒目顏色標出。

### 2. 條件組合

- 三個輸入框：**全部包含**（AND）、**任一包含**（OR）、**不包含**（NOT）。
- 同一框中的多個關鍵字以空白分隔；包含空白的片語用雙引號括起來。
- 「**正規表示式**」為進階選項，預設關閉；搜尋時顯示進度，可以取消。不提供 `*`、`?` 萬用字元。
- 可以搭配的篩選條件：
  - 時間區間（預設為整個案件）
  - 模組、Logger、等級（可複選）
  - 旗標（ADR-0004）
  - 解析欄位：Layout 元素（比對其所有別名）、命令編號、棧板編號、桶編號
- 所有條件之間為 AND。

### 3. 電話號碼

可以用電話號碼搜尋（比對原始內容）；結果中的電話號碼仍遮罩顯示，點一下才顯示完整號碼（ADR-0009）。

### 4. 結果呈現

- 結果顯示在**事件清單**，沿用 ADR-0004 的排序規則與旗標。
- 兩種模式：
  - **只顯示符合的事件**（預設）。
  - **顯示全部事件並標示符合的**；以 Ctrl + 方向鍵在符合的事件之間移動，可以看到前後文。
- 顯示符合筆數；關鍵字以醒目顏色標示；時間軸總覽上標出符合的位置。
- 點一筆結果，所有面板同步跳到該時刻（ADR-0008）。
- 修改條件後，按「**搜尋**」才重新查詢（不在輸入時即時搜尋）。
- 記住最近 **20** 次搜尋，依使用者保存；不提供具名儲存搜尋。

### 5. 效能目標

| 搜尋 | 目標 |
|---|---|
| 一般關鍵字，一天份 | **2 秒內**開始顯示結果 |
| 一般關鍵字，七天份 | **10 秒內**開始顯示結果 |
| 正規表示式 | 不設目標；顯示進度、可以取消 |

量級**假設**：一天最多 500 MB、一個案件最多 7 天（**待實際資料確認**）。

## 理由

- 工程師搜尋錯誤碼或代碼時，大小寫與全半形的差異通常沒有意義；需要精確時可以開啟區分大小寫。
- LOG 中的中文、代碼與英文常常連在一起，斷詞反而會漏找；部分比對最符合「找出所有含這串字的事件」的直覺。
- 三個輸入框可以表達 AND／OR／NOT，又不需要學語法（NFR-017）。
- 正規表示式能涵蓋萬用字元的用途；只保留一套進階規則，避免混淆。
- 錯誤碼常出現在延續行，只比對首行會漏找。
- 先解碼再比對，使用者不需要知道檔案的編碼。
- 資料都在使用者自己的電腦上，擋住電話號碼搜尋不會提高安全性，反而失去查詢簡訊通知的能力。
- 按下「搜尋」才查詢，避免在大量資料上每輸入一個字就查一次。

## 考慮過的替代方案與捨棄原因

| 方案 | 捨棄原因 |
|---|---|
| 區分大小寫為預設 | 容易漏找；保留為選項 |
| 中文斷詞後以詞比對 | LOG 中混合中文、代碼與英文，斷詞會漏找 |
| 只比對完整單字 | 找不到嵌在識別碼中的字串（例如 `Station_Storage_Unload` 中的 `Unload`） |
| 查詢語法（例如 `A AND (B OR C)`） | 需要學習語法，違反 NFR-017 |
| 同時提供萬用字元與正規表示式 | 兩套規則容易混淆 |
| 只比對訊息首行 | 延續行中的錯誤碼會漏找 |
| 禁止以電話號碼搜尋 | 沒有安全上的效果，又失去查詢能力 |
| 輸入時即時搜尋 | 大量資料時造成卡頓 |
| 具名儲存搜尋 | 第一階段先以搜尋歷史滿足需要 |

## 尚存風險

| 風險 | 影響 | 緩解方式 |
|---|---|---|
| 部分比對在大量資料上很慢 | 達不到效能目標 | 由「儲存與索引候選方案比較」評估索引方式（例如 n-gram 索引）並實測 |
| 實際量級大於假設 | 效能目標需要調整 | 取得其他廠別或忙碌日的 LOG 後重新估算 |
| 正規表示式寫錯或太複雜 | 搜尋極慢或無結果 | 顯示進度、可以取消；語法錯誤時提示 |
| 全形與半形對應規則不完整 | 少數字元比對不一致 | 以標準的 Unicode 相容分解（NFKC）處理，並以測試確認 |

## 後續驗證方式

- 以樣本確認：搜尋結果與人工比對的結果一致，不多不少（AC-001、AC-002）。
- 以 Big5 與 UTF-8 檔案中的同一個中文關鍵字搜尋，兩者都能找到。
- 以只出現在延續行的錯誤碼搜尋，可以找到並標示行號。
- 以假設量級（一天 500 MB、7 天）的測試資料驗證效能目標。
- 確認搜尋結果的順序與時間軸排序一致，重複查詢順序相同（AC-004）。

## 影響範圍

- **儲存與索引候選方案比較**：必須支援部分比對（不分大小寫、全半形相同）、整筆事件內容（含延續行）、正規表示式掃描、解析欄位篩選、依時間排序的結果，並達到第 5 點的效能目標。
