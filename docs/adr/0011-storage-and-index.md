# ADR-0011：儲存與索引

- 日期：2026-10-16
- 狀態：已接受（**待實測**）
- 確認者：repo owner（daniel579-source）
- 對應 ticket：Wayfinder「儲存與索引候選方案比較」
- 研究文件：[`docs/research/storage-index-candidates.md`（`research/storage-index` 分支）](https://github.com/daniel579-source/ai-dev-workspace/blob/research/storage-index/docs/research/storage-index-candidates.md)（不合併到 `main`）
- 相關決策：ADR-0001、ADR-0002、ADR-0004、ADR-0005、ADR-0007、ADR-0008、ADR-0009、ADR-0010

## 背景

- 限制條件：單機桌面程式、免安裝、完全離線（ADR-0001）；.NET 10（C#）、self-contained 單一資料夾、以免付費元件為主（ADR-0007）；儲存層要可以替換（ADR-0001）。
- 資料：事件的基本欄位與解析欄位、穩定識別碼與原始位置（ADR-0004、ADR-0005）；原始檔複製進案件且不得修改（ADR-0002）；Layout 快照與稽核紀錄存於案件（ADR-0006、ADR-0009）。
- 查詢：依時間穩定排序（ADR-0004）；部分比對（不分大小寫、全半形相同、含延續行）、正規表示式、AND／OR／NOT、解析欄位篩選（ADR-0010）；以命令、棧板編號串連事件；回放需要快速取得任一時刻的狀態（ADR-0008）。
- 效能目標：一般關鍵字搜尋一天份 2 秒、七天份 10 秒開始顯示結果；量級假設一天最多 500 MB、一個案件最多 7 天（ADR-0010）。
- 存放：使用者個人的資料夾；案件資料夾可整個複製當備份；可刪除；程式不加密（ADR-0009）。
- 研究（背景代理，以官方文件與授權條款為來源）比較了六個候選方案：A SQLite＋FTS5 trigram、B Lucene.NET、C LiteDB、D DuckDB、E 自訂檔案＋索引、F 混合。重要事實：
  - FTS5 trigram 索引**無法**加速少於 3 個字的子字串（例如中文兩字詞）。
  - 所有候選方案都**沒有**內建 NFKC（全半形相同）加不分大小寫的比對。
  - 企業可以用原則把「文件」資料夾靜默移到 OneDrive 同步。
  - 所有效能數字都是**估算**，尚未實測。
- 使用者確認的事實：工程師電腦使用 **SSD**；記憶體大小**待確認**；公司備份是否涵蓋 AppData **待確認**。

## 決策

### 1. 主要方案：F 混合方案（**候選方案中選定，待實測**）

- 主要儲存：**SQLite**（`Microsoft.Data.Sqlite`）。存放：
  - 事件與解析欄位
  - 命令、棧板、桶的參照表（多值欄位）；2026-10-16 #23 補充：參照表改為存放**所有**解析欄位，每一列是「事件、種類、值」，值不分大小寫
  - 狀態快照（2026-10-16 #24 修改：改為開啟案件時在記憶體中建立，每 2,000 個效果一份，**不存進 case.db**。理由：規則或 Layout 改變時不會用到過期的快照；推導只需要套用效果，速度足夠。案件資料庫改存放效果 `event_effects`，匯入與重新解析時寫入）
  - 案件中繼資料、Layout 快照、稽核紀錄
- 全文搜尋（何時用索引已依實測調整，見第 6 點）：
  - **3 個字以上的詞**：使用 **FTS5 trigram 索引**。
  - **1～2 個字的詞**、只有「不包含」條件的查詢、**正規表示式**：依日平行、依時間順序**掃描**正規化文字。
  - 2026-10-16 #21 補充：全文索引放在 `index\<日期>.db`，使用 FTS5 trigram，只記錄哪些事件含有某個 3 字片段（contentless、detail=none）；匯入完成後在背景建立。索引只產生候選，再以搜尋用文字確認，所以結果與掃描相同。每個分片記錄建立時的案件內容版本，內容改變（匯入、套用新版設定、修改偏移量）後舊分片不使用，並在背景重建。
- 儲存層以介面隔離，可以替換（ADR-0001）。

### 2. 共通設計

- **正規化的搜尋用文字**：匯入時由 .NET 產生（NFKC＋大小寫摺疊），搜尋時對查詢字串做同樣的處理。程式**不得**啟用 InvariantGlobalization，否則正規化不會生效。
  - 2026-10-16 #20 補充：搜尋用文字存在 `event_search` 資料表。正規化以「字」為單位進行，讓醒目位置對應到原文；已經是 NFKC 的訊息只做大小寫摺疊。之前建立的案件第一次搜尋時補上。
  - 掃描方式（#20）：事件序號依時間排序，所以改為依事件序號範圍分片、平行掃描（一天也再分片），取代「依日」；先以搜尋用文字篩選，再取符合的事件比對其他條件。
- **事件序號**：匯入後依 ADR-0004 的排序規則編序號，作為儲存順序，讓搜尋結果自然依時間排序、可以邊找邊顯示；穩定識別碼（ADR-0004）另外保存。
- **案件資料夾結構**：
  - **不可重建**：`case.db`（事件、欄位、參照、快照、中繼資料、稽核）、`raw\`（原始檔複本）。
  - **可重建**：`index\`（全文資料，依日分片）。刪除後可以重新建立。
  - 2026-10-16 #18 補充：不可重建的部分加上 `sources\`（原始壓縮檔，ADR-0012）與 `raw\_versions\`（重複匯入的其他版本，ADR-0002）；案件資料夾內另有一份說明檔（ADR-0009）。

### 3. 存放位置

- 預設：`%LOCALAPPDATA%\<程式名稱>\Cases\`；可以在設定中修改。
- 提供「在檔案總管開啟案件資料夾」。
- 案件位置設在 OneDrive 同步資料夾內時，顯示警告。
- 公司備份是否涵蓋 AppData **待確認**；說明文件提醒使用者自行複製案件資料夾作為備份（ADR-0009）。

### 4. 磁碟與效能

- 一個案件的磁碟用量上限：**原始 LOG 的 5 倍**。實測超過時，改為只靠掃描，不建 trigram 索引。
- 匯入：一天份（假設 500 MB）在 **2 分鐘內**完成基本匯入，之後即可瀏覽與回放；全文索引在**背景**建立，尚未建好的日期以掃描搜尋。
- 搜尋效能目標沿用 ADR-0010。
- 正式程式的實測（2026-10-16 #18，開發用電腦，熱快取，虛構資料一天 502 MB、98.5 萬筆事件）：基本匯入 **16.3 秒**，讀出所有事件 4.6 秒，合計約 21 秒（通過）；案件大小為原始 LOG 的 **3.65 倍**（尚未建立全文索引；`case.db` 保存訊息全文）。詳見 `validation/results/import-18-dev-pc.md`。
- 實測（2026-10-16 #20，條件同上，含解析欄位、效果與搜尋用文字）：一天份搜尋 **1.2～1.4 秒**（通過 2 秒的目標）；基本匯入 **34.8 秒**；案件大小為原始 LOG 的 **3.67 倍**。詳見 `validation/results/search-20-dev-pc.md`。
  - 更正：#18 的「3.65 倍」是在案件開啟中量的，包含 WAL 暫存檔（關閉時併回 case.db），實際應更小。**案件大小一律在關閉案件後量。**
- 實測（2026-10-16 #21，條件同上，含全文索引）：一天份索引建立 24.5 秒、七天份 216 秒（背景）；案件大小為原始 LOG 的 **3.90 倍**（一天）、**3.91 倍**（七天），其中索引約 0.24 倍；一般關鍵字搜尋一天份最慢 0.32 秒、七天份最慢 2.23 秒。詳見 `validation/results/search-21-dev-pc.md`。
  - 磁碟上限的做法：建立每一天的索引前，以「當天原始 LOG × 0.3」估計索引大小；加上目前的案件大小會超過 5 倍時，其餘日期不建索引，以掃描搜尋。案件大小不含 WAL 暫存檔。
  - 更正：#20 的「一天份 1.2～1.4 秒」大部分是每次搜尋前檢查「是否有缺少搜尋用文字的事件」（要掃過所有事件）；改為每次開啟案件只檢查一次後，一天份掃描約 0.2 秒。
- 2026-10-18 #47 補充：以本機的**真實樣本**（一天份 19 MB、25,337 筆事件）實測，案件大小（含全文索引，關閉後）為原始 LOG 的 **5.22 倍，未通過**上限 5 倍；未建全文索引時 4.17 倍，全文索引 1.04 倍（虛構資料為 0.23 倍）。詳見 `validation/results/real-sample-47-dev-pc.md`。
  - 原因：`case.db` 使用 4 KB 分頁，真實樣本有許多數 KB 的多行事件，跨頁存放浪費空間（訊息文字與搜尋用文字各約 18 MB，兩個資料表各約 29 MB）；全文索引建好後有 31% 是空頁。
  - 在複本上試算：分頁改為 8 KB 時 `case.db` 從 60.3 MB 降到 44.6 MB；全文索引整理後從 19.9 MB 降到 13.8 MB；合計約 4.1 倍。
  - 「當天原始 LOG × 0.3」的索引大小估計對真實樣本偏低（實際 1.04 倍，整理後約 0.73 倍），因此沒有在超過上限前停止建立索引。
  - 處理方式（分頁大小、索引建好後整理、估計係數）另開 ticket 修正，修正後重新量測真實樣本與虛構大量資料。

### 6. 實測結果（2026-10-16，開發用電腦，熱快取）

驗證程式與數據：`validation/`（#15）；摘要見 `validation/results/summary-dev-pc.md`。資料為虛構，7 天共 3,485 MB、692 萬筆事件（一天約 98.5 萬筆）。電腦：16 執行緒、64 GB 記憶體、NVMe SSD。

| 項目 | 結果 | 判定 |
|---|---|---|
| T-01 | SQLite 3.53.3，FTS5 trigram 在 self-contained 發佈中可用 | 本機通過 |
| T-03 匯入 | 一天份基本匯入 9.7 秒、7 天 39 秒；FTS5 另需一天約 37 秒 | 通過（目標 2 分鐘） |
| T-04 索引大小 | 一天：detail=full 809 MB、column 313 MB、none 117 MB（正規化文字 591 MB） | 記錄 |
| 磁碟用量 | 7 天合計原始 LOG 的 3.92 倍（不建 FTS5 約 2.3 倍） | 通過（上限 5 倍） |
| T-05～T-07 搜尋 | 七天份所有查詢 5 秒內開始顯示，多數 < 0.5 秒 | 通過（熱快取） |
| T-08 正規表示式 | 七天約 1 秒；取消後 8～71 ms 停止 | 記錄 |
| T-09 串連 | 命令、棧板編號平均 < 1 ms | 通過 |
| T-10 快照 | 從快照推導任一時刻平均 0.4 ms，與從頭推導一致 | 通過（簡化模型） |
| T-11 排序 | 重複執行與各方案的結果完全相同；時間軸單調 | 通過 |
| T-12 可攜性 | 關閉後沒有 -wal；複製後與刪除 index\ 重建後結果相同 | 本機通過；另一台電腦待測 |
| T-13 正規化 | 14 個案例全部通過 | 本機通過；其他 Windows 版本待測 |
| T-14 | 開發電腦已記錄 | 工程師電腦**待確認** |

主要發現與調整：

- **FTS5 trigram 只對罕見詞有利**。罕見詞七天份 0.01 秒；但常見詞、組合條件、搭配篩選時，FTS5 比掃描慢約 7 倍到數千倍（例如「關鍵字＋命令編號」FTS5 4.2 秒、掃描 < 0.001 秒），因為要先列出大量候選。熱快取下，SQLite 掃描七天份都在 0.5 秒內。
- **調整「何時用索引」的規則**（取代第 1 點只看字數的規則）：
  1. 有精確的篩選條件（命令、棧板、桶編號等）時，先用參照表縮小範圍，再比對文字。
  2. 3 個字以上的詞，先以索引估計符合筆數；詞很常見時改用掃描。
  3. 1～2 個字的詞、只有「不包含」、正規表示式：掃描（不變）。
- **是否保留 FTS5 暫不決定**：掃描的速度依賴資料在作業系統快取中與 NVMe SSD。冷快取與工程師電腦的結果出來後再決定；保留 FTS5 時用量約 3.9 倍，不建時約 2.3 倍。
  - 2026-10-16 #21 決定：**保留 FTS5**（開發電腦實測：罕見詞七天份從掃描 1.35 秒降到 0.08 秒，索引只多原始 LOG 的 0.24 倍）。冷快取與工程師電腦仍**待實測**。
- 2026-10-16 #21 補充：「詞很常見時改用掃描」的具體做法：以 fts5vocab 取關鍵字各 3 字片段出現的事件數，取最小值作為估計；當天估計超過 5 萬筆時改用掃描。有解析欄位的篩選時，先以參照表取候選再確認。
- 比較對象：DuckDB 每次查詢約 1～1.8 秒，比 SQLite 掃描慢；Lucene.NET 不支援 1～2 字的詞、建索引 116 秒且仍是 beta；自訂順序檔與 SQLite 掃描差不多快，但要自己維護格式。三者都沒有優勢，不採用。
- 實作注意：SQLite 連線集區會保留 ATTACH 過的資料庫，重複 ATTACH 會出錯。

## 理由

- SQLite 由 Microsoft 維護 .NET 存取層，授權寬鬆（公有領域＋Apache-2.0＋MIT），單一檔案，適合結構化欄位、多值參照與狀態快照；原生 DLL 約 2 MB，可以放進 self-contained 資料夾。
- trigram 索引能加速 3 個字以上的部分比對；短詞與正規表示式本來就無法用索引，改用依日平行掃描，在 SSD 上估算可以達到目標。
- 正規化文字由程式統一產生，不依賴各儲存引擎不完整的大小寫與全半形處理。
- 事件序號讓結果自然依時間排序，不必每次查詢都重新排序。
- 不可重建與可重建的資料分開，索引損壞或格式升級時只要重建 `index\`。
- `%LOCALAPPDATA%` 屬於使用者個人、不漫遊、不在 OneDrive 已知資料夾移動的範圍內，避免真實 LOG 被同步到雲端（CLAUDE.md 第 13 條）。
- 背景建立索引，使用者不必等索引建完就能開始分析。

## 考慮過的替代方案與捨棄原因

| 方案 | 捨棄原因 |
|---|---|
| A. 只用 SQLite＋FTS5 trigram | 短詞（中文兩字詞）與正規表示式沒有對策；F 已包含 A 的優點 |
| B. Lucene.NET | 4.8 版仍為 beta；狀態快照與結構化欄位需要第二套儲存；保留為實測比較對象 |
| C. LiteDB | 沒有全文搜尋；排序規則綁定建立案件那台電腦的文化設定 |
| D. DuckDB | 原生 DLL 約 37 MB；子字串沒有索引；正規表示式語法與 .NET 不同；保留為實測比較對象 |
| E. 自訂檔案格式＋自建索引 | 自建格式的維護風險高 |
| 案件放在「文件」資料夾 | 企業可能靜默同步到 OneDrive，真實 LOG 會上雲 |
| 案件放在 `%APPDATA%`（Roaming） | 網域環境可能漫遊同步，不適合 GB 級資料 |
| 匯入時一次建好全部索引 | 匯入時間過長，延後開始分析 |

## 尚存風險

| 風險 | 影響 | 緩解方式 |
|---|---|---|
| 所有效能數字都只是估算 | 實作後才發現達不到目標 | 先做技術驗證（T-01～T-14）；開發電腦熱快取的結果見第 6 點 |
| 冷快取或記憶體較小的電腦上，掃描變慢 | 短詞與常見詞搜尋達不到目標 | 重新開機後量測冷快取；在工程師電腦重跑量測；保留 FTS5 作為罕見詞的加速 |
| 索引用於常見詞或搭配篩選時反而更慢 | 搜尋比掃描慢數倍到數千倍 | 依第 6 點的規則選擇索引或掃描 |
| trigram 索引超過磁碟用量上限 | 案件太大 | 改為只靠掃描；或調整 FTS5 的 `detail` 選項 |
| 記憶體不足以支撐平行掃描 | 七天份搜尋變慢 | 確認工程師電腦的記憶體；限制平行度 |
| 公司備份不涵蓋 AppData | 使用者以為有備份 | 說明文件提醒；可改設定位置 |
| SQLite WAL 模式下複製案件資料夾不完整 | 備份的案件無法開啟 | 程式關閉案件時做 checkpoint；說明「關閉案件後再複製」 |
| 正規化規則與畫面顯示不一致 | 搜尋結果與醒目標示位置對不上 | 保留原文與正規化文字的位置對應，並以測試確認 |

## 後續驗證方式

- 技術驗證：研究文件第 8 節 T-01～T-14，包含匯入時間、索引大小、一天與七天的搜尋時間、短詞與正規表示式掃描、狀態快照讀取速度。
- 以假設量級（一天 500 MB、7 天）的虛構或本機測試資料執行；真實 LOG 只在本機使用（ADR-0009）。
- 確認案件資料夾整個複製到另一台電腦後可以開啟，`index\` 刪除後可以重建。
- 確認 `%LOCALAPPDATA%` 與 OneDrive 警告在一般與網域帳號下都正確。

- **技術驗證**（ADR-0007）：加入本 ADR 的實測項目。
