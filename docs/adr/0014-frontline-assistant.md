# ADR-0014：第一線問答助理

- 日期：2026-10-21
- 狀態：**提議中**（技術依 ADR-0013 的候選方案；取得指定的 AI 筆電並實測後才改為已接受）
- 確認者：repo owner（決策內容，2026-10-21）；接受與否待實測
- 相關 ADR：ADR-0001、ADR-0009、ADR-0013
- 對應 ticket：#55

## 背景

最終目標是讓「知識庫加本機 LLM」代替工程師回覆現場第一線人員的問題，並給出解決辦法。使用者因此從工程師擴大到第一線人員。

第一線人員可能直接照著建議操作設備；錯誤的建議可能造成人員受傷或設備損壞。ADR-0013 第 5 點原本只讓 LLM 做「轉換」與「摘要」，本 ADR 規定 AI 回覆第一線時的範圍、轉交工程師的條件與安全規則。

## 決策（提議）

1. **使用者**：
   - 第一線人員：描述問題與現況，取得回覆。
   - 工程師：接手轉交的問題、核准回覆、維護知識庫與安全清單。
2. **必須先匯入 LOG**：即使問的是「現在」的問題，也要先把有問題時段的 LOG 匯入成案件才能分析，不做即時讀取。第一線人員或工程師都可能匯入，匯入流程要讓第一線也能操作。沒有開啟案件，或案件的時間範圍不涵蓋問題發生的時間時，AI 不回答，只提示先匯入。
3. **給第一線的處置只來自知識庫**：AI 只負責理解問題、找出相關的事件與警報代碼、選出適用的知識庫條目。處置文字原文引用知識庫並附出處；知識庫沒有的處置，AI 不產生。
4. **依執行者區分**：知識庫增加「執行者」欄，值為「現場可執行」或「限工程師」；沒有填的一律視為「限工程師」。
   - 現場可執行：AI 回覆第一線（受第 7 點的分階段限制）。
   - 限工程師：給第一線的回覆只說明原因並請他們聯絡工程師，不給操作步驟。轉交給工程師的內容包含原因說明與**參考解決方案（含詳細的操作步驟）**，並醒目標示「僅供參考，需由工程師判斷後執行」。
   - 參考方案的來源：知識庫有對應處置時以知識庫為準並附出處；知識庫沒有時，AI 可以產生參考步驟，每一步標示「AI 產生，未經知識庫驗證」，這類內容只給工程師。
5. **安全清單**：
   - 檔案：全公司共用一份 `safety.csv`，每個廠別可以另加一份補充 `<廠別>.safety.csv`；都只放在本機，不進 repo（ADR-0009）。
   - 欄位：類別、關鍵字或情境、警報代碼（可省略）、對第一線的指示、出處。
   - 第一線的描述或案件中的事件符合清單任一項時：「對第一線的指示」原文顯示給第一線，AI 不改寫；AI 不給第一線任何操作步驟，一律轉交工程師。
6. **轉交工程師**：
   - 條件（任一項成立）：知識庫沒有對應條目；處置屬於「限工程師」；符合安全清單；找不到對應的事件，或事件和描述不一致。
   - 方式（第一版）：在案件資料夾內產生轉交摘要（描述、事件序號與警報、比對過的知識庫條目、參考方案）。工程師以公司核准的內部方式取得案件，以 LogTrace 開啟後看到轉交摘要，點選可以跳到事件。案件含有真實 LOG，傳遞依 ADR-0009。
7. **分階段導入**：
   - 第一階段：所有回覆先由工程師確認或修改，才給第一線，並累積紀錄。
   - 第二階段（白名單）：某個警報代碼累積至少 20 次、照原樣送出的比率 ≥ 95%、「該轉交卻沒轉交」0 次，經指定的資深工程師核准（記錄核准者與日期）後列入白名單，由 AI 直接回覆第一線。出錯一次立即移出，回到第一階段。「限工程師」或符合安全清單的代碼不能列入。
8. **問答紀錄**：每次問答記錄問題、AI 的回答與引用的出處、是否轉交、工程師的修改、最後實際的處理結果，以及白名單的核准與移出，作為稽核、計算正確率與改進知識庫的依據。單純查詢知識庫仍不記錄（ADR-0013 第 2 點）；回覆第一線的建議要記錄。
9. **執行環境**：第一版以一台指定的 AI 筆電為目標，其他電腦待確認。LLM 一律在本機離線執行（ADR-0001、ADR-0009、ADR-0013）。
10. **可追溯性**：回覆中的每一句都附上事件序號或知識庫出處，點選可以跳到原始事件或條目（CLAUDE.md 3.4 節）。

## 理由

- 處置只引用知識庫，加上「執行者」分級與安全清單，把小模型產生錯誤步驟的風險限制在工程師這一層；工程師有能力判斷參考方案。
- 規定先匯入 LOG，回答才有事實依據，也不必改動 ADR-0001、ADR-0002 的事後匯入架構。
- 轉交摘要放在案件中，不需要伺服器；工程師不在現場、也不用同一台筆電時仍可接手（2026-10-21 由 Jev 判斷，信心度 0.89）。
- 先由工程師把關，再以白名單逐步放手，先累積正確率的證據再擴大範圍。

## 考慮過的替代方案與捨棄原因

| 方案 | 捨棄原因 |
|---|---|
| AI 自由產生處置，直接給第一線 | 可能產生錯誤步驟，造成人員受傷或設備損壞 |
| 限工程師的條目只說明原因、不給方案 | 工程師接手時要從頭查，失去節省時間的效益 |
| 即時讀取 LOG | 要改動匯入架構與 ADR-0001；即時資料不完整，判斷不可靠 |
| 轉交用程式內的待處理清單 | 需要共用的存放位置；工程師不一定使用同一台筆電 |
| 安全情境由 AI 判斷，不另建清單 | 安全判斷不能交給模型推測 |
| 修改 ADR-0013，不另開新 ADR | 使用者與安全規則屬於另一層決策，混在一起不易維護 |

## 尚存風險

| 風險 | 影響 | 緩解方式 |
|---|---|---|
| 「執行者」欄填錯，危險操作標成「現場可執行」 | 第一線執行危險操作 | 條目經工程師審核；白名單排除限工程師的代碼 |
| 安全清單漏列情境 | 該轉交的沒有轉交 | 負責單位定期檢討；從問答紀錄找出漏列的情境 |
| 第一線的用詞與清單關鍵字不同 | 安全清單沒有觸發 | 比對時正規化；之後評估向量搜尋比對意思相近的描述（ADR-0013 第 3 點） |
| AI 產生的參考步驟有誤 | 誤導工程師 | 只給工程師，並醒目標示僅供參考 |
| 匯入的 LOG 時間不對 | 依錯誤的事件回答 | 檢查案件時間範圍，不涵蓋就不回答 |
| 小模型的中文理解與判斷力不足 | 選錯條目 | 以虛構情境評估；第一階段由工程師把關 |
| 轉交摘要隨案件傳遞，案件含真實 LOG | 外流風險 | 只用核准的內部方式傳遞（ADR-0009） |

## 後續驗證方式

- 在指定的 AI 筆電上以虛構資料量測速度與記憶體用量（可以與 #47 一起進行）。
- 以虛構情境集量測：選對知識庫條目的比率、「該轉交卻沒轉交」的次數、安全清單觸發的正確率、時間範圍不符時是否拒答。
- 第一階段累積實際紀錄後，檢討白名單門檻是否合適。
