# ADR-0015：知識檢索採規則關聯圖加向量搜尋

- 日期：2026-11-04
- 狀態：**提議中**（技術全部為**候選方案**；依 ADR-0013、ADR-0014，取得現場硬體並實測後才改為已接受）
- 確認者：repo owner（決策內容，2026-11-04）；接受與否待實測
- 相關 ADR：ADR-0003、ADR-0005、ADR-0006、ADR-0008、ADR-0011、ADR-0013、ADR-0014
- 對應 ticket：待開立

## 背景

ADR-0013 第 3 點把「向量搜尋（sqlite-vec 加小型 embedding 模型）」列為知識庫的下一步，供 ADR-0014 的第一線問答助理找出相關的知識庫條目。

使用者提出改用 GraphRAG 的構想。GraphRAG 一般指由 LLM 讀取文件、抽出實體與關係建成知識圖，檢索時沿圖展開，再交給 LLM 回答。

本專案的特性：

- 核心目標是還原多台設備之間的關聯與事件順序。
- 系統裡已經有程式依規則建立的關係：
  1. 命令、棧板、桶編號串接不同模組的事件（ADR-0005）。
  2. 佈局中輸送線與搬送機的連接（ADR-0006）。
  3. 警報代碼對應知識庫條目（ADR-0013 第 2 點）。
  4. 安全清單（ADR-0014 第 5 點）。
- 知識庫第一版是結構化的 CSV，不是大量沒有結構的長篇文件。真實知識庫文件的格式**待確認**。
- LLM 只在筆電本機離線執行，模型為 3～8B（ADR-0013），現場硬體規格**待確認**。
- 給第一線的處置只原文引用知識庫，安全判斷不交給模型（ADR-0014）。

## 決策（提議）

1. **不採用由 LLM 抽取建圖的 GraphRAG 作為主要做法**。檢索改為兩種方式並用：「規則關聯圖」找出有關係的事實，「向量搜尋」比對意思相近的描述。
2. **規則關聯圖**：關係只來自程式依規則可以確定的資料，不由 LLM 產生。第一版的關係類型（**候選**）：

   | 關係 | 來源 | 追溯資訊 |
   |---|---|---|
   | 事件 → 警報代碼 | 廠別設定的解析規則抽出的欄位 | 事件序號、原始檔與行 |
   | 警報代碼 → 知識庫條目 | 完全比對（ADR-0013 第 2 點） | 知識庫檔名與行號 |
   | 事件 ↔ 事件（同一命令、棧板或桶） | 命令串接（ADR-0005） | 事件序號、識別碼 |
   | 設備 ↔ 設備（上下游） | 佈局的輸送線連接（ADR-0006） | 廠別設定修訂版本、元件 ID |
   | 知識庫條目或描述 → 安全清單 | 關鍵字或警報代碼比對（ADR-0014） | 安全清單檔名與行號 |

   每一條關係都要附上追溯資訊；沒有來源的關係不使用。
3. **展開方式**：從問題的時間範圍與案件出發，依序展開：
   1. 範圍內的事件。
   2. 這些事件的警報代碼。
   3. 對應的知識庫條目。
   4. 再沿命令串接與佈局上下游，找出相關設備在同一段時間的事件與警報。

   展開的層數與時間窗大小**待確認**，由實測決定。只有展開後的結果送給 LLM（ADR-0013 第 5 點）。
4. **存放**：不採用圖資料庫，也不另外架設伺服器（ADR-0001）。關係在查詢時從案件資料與廠別設定計算；如果效能需要，再把邊表存在案件的 SQLite 中（ADR-0011）。是否需要存放，由實測決定。
5. **向量搜尋**：保留 ADR-0013 第 3 點的候選方案（sqlite-vec 加小型 embedding 模型），處理第一線的用詞和知識庫或安全清單關鍵字不同的情況（ADR-0014 的尚存風險）。向量搜尋只用來**找出候選條目**，最後顯示的內容仍是知識庫原文與出處。
6. **時間與排序**：
   - 展開時依 ADR-0003，照 LOG 記錄的時間與使用者手動設定的偏移量計算，不自動校正時鐘偏差。
   - 時間窗內跨模組的先後順序，沿用 ADR-0003 第 6 點的不確定性標示。
   - 時間窗涵蓋 ADR-0008 標示的「這段時間沒有 LOG」時，展開結果要提示可能有缺漏。
7. **關係不等於因果**：佈局上下游、同一時間窗內同時出現的警報，只表示「可能相關」，畫面與回覆都不得寫成因果。這是**假設**，要標示清楚。
8. **LLM 抽取建圖保留為日後選項**：只有在確認知識庫文件是大量沒有結構的手冊，而且以虛構資料評估後確實需要時才另外討論。屆時抽出的關係要經工程師審核才能使用；未審核的一律標示「AI 推測」，只給工程師看，不用於回覆第一線。
9. **可以降級**：沒有 LLM 或 embedding 模型時，規則關聯圖仍可單獨使用，以清單方式顯示相關事件與知識庫條目，不需要 AI。

## 理由

- 規則建立的關係每一條都能追溯到事件、設定或知識庫的行號，符合 CLAUDE.md 3.4 節與 ADR-0013、ADR-0014「事實由引擎決定」的原則。
- 不需要 LLM 就能建圖，不受現場硬體規格未定的影響，可以先以虛構資料驗證。
- 本專案需要的「設備關聯」已經存在於命令串接與佈局中，不必再由 LLM 推測。
- 知識庫第一版是結構化資料；GraphRAG 擅長的大量非結構文件，在本專案尚未確認存在。
- 向量搜尋補上規則比對不到的同義描述，兩者分工明確。

## 考慮過的替代方案與捨棄原因

| 方案 | 捨棄原因 |
|---|---|
| LLM 抽取建圖的 GraphRAG（例如 Microsoft GraphRAG、LightRAG） | 建圖需要大量呼叫 LLM，筆電上的小模型速度與品質不足；抽出的關係可能有錯又沒有原始出處，違反可追溯性；錯誤關係進入第一線回覆有安全風險（ADR-0014）。保留為第 8 點的日後選項 |
| 只用向量搜尋（維持 ADR-0013 第 3 點原案） | 找不到跨設備、跨事件的關聯，無法利用命令串接與佈局 |
| 只用規則關聯圖 | 第一線的用詞和知識庫不同時比對不到 |
| 採用圖資料庫（例如 Neo4j 伺服器版） | ADR-0001 不另外架設伺服器；資料量預期不需要 |
| 採用內嵌式圖資料庫 | 增加相依套件與授權確認；SQLite 查詢應已足夠，待實測不足時再評估 |

## 尚存風險

| 風險 | 影響 | 緩解方式 |
|---|---|---|
| 展開範圍過大 | 送給 LLM 的內容超過可處理的長度，或回應太慢 | 限制層數與時間窗；以虛構資料量測 |
| 展開範圍過小 | 漏掉真正相關的設備或警報 | 以虛構情境集量測召回率；工程師可以調整範圍 |
| 使用者把「可能相關」誤認為因果 | 誤導排查方向 | 第 7 點標示；回覆文字不得使用因果用語 |
| 廠別沒有設定佈局連接或警報代碼欄位 | 部分關係無法建立 | 退回以時間窗與關鍵字搜尋；在結果中說明缺少哪些關係 |
| 命令串接在部分模組無法使用 | 跨模組關聯不完整 | 依 ADR-0005 現有的處理；結果中說明 |
| 真實知識庫文件的格式未知 | 第 8 點的需求可能提早出現 | 取得去識別化樣本後重新評估 |
| embedding 模型的中文能力不足 | 向量搜尋找錯條目 | 以虛構資料評估候選模型；最後內容仍是知識庫原文 |

## 後續驗證方式

- 以虛構的案件、佈局、知識庫與安全清單，建立情境集，量測：
  - 選對知識庫條目的比率；
  - 相關設備與警報的召回率；
  - 展開結果的大小；
  - 查詢時間。
- 與「只用向量搜尋」比較同一份情境集的結果。
- 在現場 AI 筆電上量測展開加上 LLM 回覆的總時間（可以與 ADR-0013、ADR-0014 的實測一起進行）。

## 待確認

1. 展開的層數與時間窗的預設值。
2. 真實知識庫文件的格式與數量（同 ADR-0013 待確認第 2 點）。
3. 佈局的上下游連接是否足以代表設備之間的實際關聯。
4. 邊表是否需要存入案件 SQLite。
