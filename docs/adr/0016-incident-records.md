# ADR-0016：異常紀錄與經驗累積

- 日期：2026-11-13
- 狀態：**提議中**（技術依 ADR-0013 的候選方案；取得現場硬體並實測後才改為已接受）
- 確認者：repo owner（決策內容，2026-11-13）；接受與否待實測
- 相關 ADR：ADR-0002、ADR-0009、ADR-0013、ADR-0014、ADR-0015
- 對應 ticket：#107；實作 #110（不需要 LLM 的部分）

## 背景

使用者對知識庫提出三個目標（2026-11-13）：

1. 現場卡住時立刻保存 LOG，交給 LogTrace 解析後，在 LLM 的對話畫面回答「為什麼卡住」與「應該怎麼處理」；處理完異常後，把相關資訊整理、記錄並加進知識庫。
2. 知識庫能依過去處理異常的經驗，提高日後處理同類異常的能力。
3. 使用者可以透過一般對話與 LLM 應答，或操作筆電。

現場可以當作知識庫來源的文件有：警報代碼表、設備操作手冊、SOP／處置程序，以及過去的維修紀錄（2026-11-13 使用者提供）。各文件的格式**待確認**。

和現有決策的關係（2026-11-13 由 Jev 判斷）：

| 陳述 | Jev（noul） |
|---|---|
| 由 LLM 斷定「為什麼卡住」會與 ADR-0015 第 7 點（關係不等於因果）衝突 | 0.90 |
| 由 LLM 給出知識庫以外的處置會與 ADR-0014 第 3 點衝突 | 0.94 |
| 「處理完後加進知識庫」的做法，現有 ADR 已經決定 | 0.25 |

目標 3 中「操作筆電（Windows 或其他程式）」牽涉資訊安全與 IT 核准，使用者決定**暫緩**，不寫進本 ADR，也不寫進其他 ADR；之後要做時另外討論。以對話查詢 LogTrace 維持 ADR-0013 第 5 點（自然語言轉搜尋條件）。

## 決策（提議）

1. **LOG 維持手動匯入**：卡住時由現場人員或工程師保存 LOG，依 ADR-0002 手動匯入成案件後再分析。ADR-0002 不變；ADR-0014 第 2 點「先匯入 LOG 才回答」不變。
2. **知識庫分成兩類內容**：
   - **參考資料**：警報代碼表、操作手冊、SOP。第一版仍是 ADR-0013 第 2 點的 `<廠別>.kb.csv`；手冊與 SOP 原文如何收錄，待取得文件樣本後另外決定。
   - **異常紀錄**：一次已處理完的異常，經工程師審核。內容（**候選**欄位）：現象、發生的時間範圍、廠別與案件、相關事件序號與警報代碼、相關設備、確認的原因、處置、結果、執行者（依 ADR-0014 第 4 點）、撰寫者、審核的工程師與日期、狀態（草稿／已審核／停用）。
     - 2026-11-13 補充（雛形試用後，#107）：欄位加上**停機時間、處理人、照片或文件**；狀態加上「修訂中」（第 3 點）。照片或文件的存放位置與機密等級**待確認**（ADR-0009）。
     - 2026-11-13 補充（實作，#110）：**停機時間**為自由文字（例如「約 45 分鐘」），格式待確認（Jev 0.97）。**照片或文件**欄位先不做，存放位置與機密等級決定後另外處理（使用者決定；Jev 0.49 信心度不足）。
3. **異常紀錄的產生與審核**：
   - 異常處理完成後，AI 從案件（事件、警報、命令串接）與問答紀錄（ADR-0014 第 8 點）產生異常紀錄的**草稿**。草稿中每一項事實都附事件序號或問答紀錄的出處；AI 推論的內容標示「AI 推測」。
   - 工程師審核、修改後才改為「已審核」，正式列入知識庫。草稿只給工程師看。
   - 過去的維修紀錄也整理成同樣的格式，同樣經工程師審核後才列入。整理方式（人工或 AI 協助）待取得維修紀錄的格式後決定。
   - 審核過的紀錄有錯時，改為「停用」，不刪除（保留稽核依據）。
   - 2026-11-13 補充（雛形試用後，#107；雛形在 `prototype/incident-records` 分支）：
     1. **版本**：每次審核通過成為新的一版，保存完整內容。
     2. **修訂中**：修改已審核的紀錄時改為「修訂中」，**舊版繼續有效**，查詢仍顯示舊版；可以放棄修改。修改內容審核通過後成為新的一版。
     3. **改過的地方要顯眼**：最新一版相對於前一版改過的欄位，在查詢結果（工程師與第一線）與詳細畫面都標示；修訂中尚未審核的變更，在詳細畫面另外標示（範圍與位置由 Jev 判斷，信心度 0.92、0.79）。
     4. **修訂經過**：保存每一版的審核者、日期，以及每個欄位「舊 → 新」。
     5. **停用後可以恢復**：退回草稿，重新審核通過後成為新的一版；審核通過前，查詢中仍然沒有這筆。
     6. **維修紀錄原文**：審核通過就算確認，不必逐欄確認。
     7. **撰寫者與審核者同一人**：只提醒，不擋下；誰可以審核仍**待確認**。
     8. **待審核清單**：列出草稿與修訂中，**包含還不能審核的**；每項顯示種類（新草稿、維修紀錄、修訂中、恢復）、等待時間、擋下的原因與提醒；可以審核的排前面，同類依等待時間由久到新（排序由 Jev 判斷，信心度 0.88）。審核通過、放棄修改或停用後離開清單。
     9. **審核擋下的條件（雛形採用）**：現象、原因、處置任一項仍是 AI 推測；現象、原因、處置、結果有空白；從案件產生的紀錄沒有相關事件。只提醒的條件：執行者空白、維修紀錄沒有事件序號、撰寫者與審核者同一人、和上一版相比沒有修改。
   - 2026-11-13 補充（實作，#110）：
     1. **誰可以審核：先不限制**（使用者決定）。審核者就是「異常紀錄」面板上的「使用者」，預設為 Windows 使用者名稱，可以修改；沒有填審核者時擋下。
     2. **只提醒的條件**：審核通過前列出提醒並要求確認，確認後才通過；提醒內容保存在該版。
     3. **從未審核過的草稿也可以停用**（附理由，離開待審核清單）；草稿內容保留，恢復後繼續使用（使用者決定；Jev 0.50 信心度不足）。修訂中停用時，尚未審核的修改不保留。
     4. **AI 推測的確認方式**：現象、原因、處置各有「AI 推測」勾選框，取消勾選表示已確認（使用者決定；Jev 0.16 信心度不足）。AI 推測的標記改變也算該欄位改過。
4. **存放**：每個廠別一個資料夾 `<廠別>.incidents\`，放在廠別設定旁邊，每筆紀錄一個 JSON 檔（**候選**格式），記錄引用的案件名稱與事件序號。屬於廠別的本機資料，與知識庫一樣**不進 repo**（ADR-0009）；repo 只放虛構的範例與測試資料。紀錄引用的案件不在這台電腦時，紀錄仍可以閱讀，只是不能跳到事件。
   - 2026-11-13 補充（實作，#110；使用者決定）：
     - **檔名**：紀錄編號以時間編號 `IR-年月日-時分秒-4 碼亂數`，檔名為編號加 `.json`，不同電腦同時建立也不會撞號。JSON 含格式版本，版本較新或內容有誤的檔案不使用，列出檔名與原因。
     - **多台電腦同時修改**：存檔前比對讀取時的檔案內容，已被別人修改（或刪除）時不覆寫，提示重新載入；先寫暫存檔再取代。
     - **引用的事件**：保存事件序號（只做顯示）、穩定識別碼（ADR-0004 第 2 點，跳到事件時使用，Jev 0.76）、時間、模組與**遮罩後**的訊息（最多 300 字；不論畫面是否顯示敏感資訊一律遮罩，ADR-0009）。只在紀錄引用的案件就是目前開啟的案件時可以跳到事件。加入事件時一併帶入該事件的警報代碼與設備編號（Jev 0.67），工程師可以修改。
     - **找不到廠別設定檔時不能使用**（資料夾的位置依設定檔決定）。
     - **畫面**：新增獨立的「異常紀錄」面板（預設版面中自己一個窗格，Jev 0.80），內含查詢（只列有效版本）、待審核、停用三個分頁，以及詳細資訊、相關事件、編輯與修訂經過。
5. **經驗的累積方式**：累積已審核的異常紀錄，發生新的異常時以檢索找出「過去相似的異常」。**不以過去的紀錄微調（fine-tune）模型**。
6. **找出相似案例**：沿用 ADR-0015。先以警報代碼與相關設備（規則關聯圖）找出候選，再以向量搜尋比對「現象」描述。顯示時一律稱為「過去相似的異常」，附紀錄出處，不寫成「同一個原因」。
   - 2026-11-13 補充（雛形試用後，#107）：工程師與第一線的相似查詢都只列**目前有效的版本**，**不列草稿**；停用的紀錄不列入。草稿由第 3 點的待審核清單處理。
7. **放寬 AI 推論（只給工程師）**：
   - LLM 可以根據案件中的事件、規則關聯圖展開的結果與相似的異常紀錄，推論「可能為什麼卡住」與「可能的處置」。
   - 推論內容一律標示「**AI 推測**」，引用的事件與紀錄附出處，**只給工程師看**。
   - 已審核的異常紀錄與知識庫條目中的原因與處置，以原文引用並附出處，不標示 AI 推測。
8. **給第一線的內容不變**：仍依 ADR-0014 第 3 點，只原文引用知識庫條目或**已審核**的異常紀錄，並附出處；「AI 推測」不給第一線。已審核的異常紀錄視同知識庫條目，同樣依「執行者」欄、安全清單與白名單（ADR-0014 第 4、5、7 點）處理。
9. **不改變的原則**：LLM 只在本機離線執行（ADR-0013 第 4 點）；送給 LLM 的只有篩選與展開後的事件（ADR-0013 第 5 點）；可以降級，沒有 LLM 時異常紀錄仍可以手動建立、閱讀與搜尋。

## 理由

- 審核過的異常紀錄每一筆都有出處與審核者，回答「過去類似情況的原因與處置」時可以追溯，也不必把相關性寫成因果（ADR-0015 第 7 點）。
- 檢索不需要重新訓練模型，筆電上可以做到；紀錄有錯時改為停用就立即生效，微調則無法移除已學到的錯誤。
- 讓 AI 產生草稿、工程師審核，可以減少工程師整理紀錄的時間，又不讓未經確認的內容進入給第一線的回覆。
- AI 推測只給工程師，與 ADR-0014 第 4 點「AI 產生的參考步驟只給工程師」一致，第一線的安全規則不變。
- 每筆紀錄一個 JSON 檔：一筆紀錄有多個事件序號與較長的說明，CSV 不便於在 Excel 整理；一筆一檔也方便停用、搬移與比較。
- 2026-11-13 補充（雛形試用後，#107）：修訂期間舊版繼續有效，查詢不會因為正在修改而少了一筆經驗；保存每一版並標示改過的地方，工程師與第一線都能知道內容變過，稽核時也能還原當時引用的是哪一版。待審核清單列出還不能審核的紀錄，工程師才看得到哪些 AI 推測還沒處理、哪些紀錄放了很久。

## 考慮過的替代方案與捨棄原因

| 方案 | 捨棄原因 |
|---|---|
| 維持 ADR-0013、0014 原狀，LLM 不推論原因與處置 | 知識庫沒有的異常就完全沒有建議，工程師仍要從頭查；使用者選擇放寬（只給工程師） |
| AI 推測也給第一線 | 可能產生錯誤步驟，造成人員受傷或設備損壞（ADR-0014 捨棄理由相同） |
| 以過去的紀錄微調本機模型 | 結果難以追溯；學錯的內容無法移除；需要另外的訓練硬體與資料整理 |
| AI 自動把異常紀錄列入知識庫，不經審核 | 錯誤的原因或處置會被引用給第一線 |
| 工程師從頭手寫異常紀錄，不由 AI 產生草稿 | 工程師負擔大，紀錄容易累積不起來；手寫仍然可以，作為降級方式 |
| 異常紀錄寫進 `<廠別>.kb.csv` | 欄位多、說明長、有多個事件序號，不適合一列表示 |
| 異常紀錄存在案件內 | 案件可能被刪除或只在某台電腦；經驗要跨案件累積 |
| 修改 ADR-0002，做一鍵收集 LOG | 使用者決定維持手動匯入 |
| 修改已審核紀錄時直接改，不保留舊版（2026-11-13） | 無法知道改過什麼，也無法還原當時引用的內容 |
| 修改期間把紀錄下架，審核通過才重新列入（2026-11-13，雛形第 1 版） | 修改期間查不到這筆經驗；使用者決定舊版繼續有效 |
| 標示所有曾經改過的欄位（2026-11-13） | 改過多次後幾乎每個欄位都被標示，看不出最近改了什麼；完整經過改由修訂經過呈現 |
| 相似查詢也列出草稿（2026-11-13，雛形第 1 版） | 只是查詢時，未審核的 AI 推測是干擾；草稿改由待審核清單處理 |
| 待審核清單只列可以審核的（2026-11-13） | 看不到還有 AI 推測未處理、或放了很久的紀錄 |
| 停用後不能恢復（2026-11-13，雛形第 1 版） | 停用的理由可能事後被推翻；改為退回草稿重新審核 |
| 撰寫者與審核者同一人時擋下（2026-11-13） | 誰可以審核仍待確認；使用者決定先只提醒 |

## 尚存風險

| 風險 | 影響 | 緩解方式 |
|---|---|---|
| 工程師沒有時間審核，草稿堆積 | 經驗累積不起來 | 草稿列出待審核清單；審核只需修改，不必從頭寫 |
| 審核過的紀錄原因判斷錯誤 | 錯誤經驗被重複引用 | 可以停用；問答紀錄中工程師的修改可以找出有問題的紀錄 |
| 工程師把「AI 推測」當成事實 | 誤導排查方向 | 醒目標示；與已審核內容分開顯示 |
| 相似案例檢索找錯 | 引用不相干的經驗 | 顯示比對到的警報代碼、設備與相似度；以虛構情境集量測 |
| 異常紀錄含真實設備資訊與 LOG 摘錄 | 外流風險 | 存放在本機，不進 repo；傳遞依 ADR-0009 |
| 引用的案件已刪除或不在同一台電腦 | 不能跳到原始事件 | 紀錄保存事件的關鍵內容（已遮罩）與案件名稱；不能跳轉時提示 |
| 過去維修紀錄的格式不一致 | 整理成本高 | 取得樣本後決定整理方式 |
| JSON 格式不便工程師直接編輯 | 只能在 LogTrace 中編輯 | 在 LogTrace 提供編輯畫面；格式為候選，實作時再確認 |
| 修訂次數多，版本與修訂經過變大（2026-11-13） | 檔案變大、畫面變長 | 查詢只顯示有效版本與最新一版的變更；完整經過另外展開 |
| 撰寫者與審核者同一人只提醒（2026-11-13） | 等於沒有第二人確認 | 待審核清單與修訂經過顯示提醒；確認「誰可以審核」後再決定是否擋下 |
| 照片或文件含機密（2026-11-13） | 外流風險 | 存放位置與機密等級待確認，依 ADR-0009 處理 |

## 後續驗證方式

- 以虛構的案件、問答紀錄與異常紀錄建立情境集，量測：
  - AI 草稿中事實出處的正確率、工程師需要修改的比例；
  - 相似異常的檢索命中率（與 ADR-0015 的情境集一起）；
  - AI 推測與已審核內容是否確實分開、第一線是否看不到 AI 推測。
- 2026-11-13：以虛構資料的雛形（`prototype/incident-records` 分支）確認流程、版本與待審核清單，使用者試用後的結論已寫入第 2、3、6 點；實作時以虛構資料測試修訂中舊版仍有效、改過欄位的標示、恢復、待審核清單的排序。
- 2026-11-13（#110）：上述項目已以虛構資料的自動測試確認（引擎、畫面模型、UI 冒煙測試），另含存檔衝突、讀不了的檔案、加入事件時遮罩訊息、跳到事件。尚待在現場以實際的異常整理幾筆紀錄，確認欄位與流程是否好用。
- 取得過去維修紀錄的去識別化樣本後，確認欄位是否足夠、整理方式。
- 在現場 AI 筆電上量測產生草稿的時間（可以與 ADR-0013、ADR-0014 的實測一起進行）。

## 待確認

1. 各類文件（代碼表、手冊、SOP、維修紀錄）的格式、數量與機密等級。
2. 手冊與 SOP 原文如何收錄（只連結原文、全文搜尋，或只整理成 CSV）。
3. 異常紀錄的欄位：2026-11-13 已用雛形確認並補上停機時間、處理人、照片或文件（#107）；取得真實維修紀錄樣本後再確認一次。由誰負責審核：2026-11-13 先不限制、只提醒同一人（#110）；日後需要限制時再決定。
4. 「操作筆電」功能（暫緩，另外討論）。
5. 照片或文件的存放位置與機密等級（2026-11-13）。
