# ADR-0023：知識庫的定期總結與跨廠共用

- 日期：2026-11-17
- 狀態：**提議中**（做法由使用者決定；實作與虛構資料驗證後才改為已接受）
- 確認者：repo owner（決策內容，2026-11-17）
- 相關 ADR：ADR-0013（知識庫與本機離線 LLM）、ADR-0014（第一線問答助理）、ADR-0015（知識檢索）、ADR-0016（異常紀錄）、ADR-0021（機密規格書與共用層）、ADR-0022（向量搜尋）
- 對應 ticket：#107（異常紀錄）；實作 #167（已過時，完成）、#168（每廠總結，完成）、#169、#170（多廠共用）、#171（向量搜尋，完成）

## 背景

知識庫分成三層（ADR-0013、ADR-0016、ADR-0021）：

| 層 | 是否隨廠別增加 |
|---|---|
| 共用的設備對照表（依設備種類 RM、STV、AGC 各一份） | 不會，各廠共用 |
| 各廠補充與警報代碼表（`<廠別>.kb.csv`） | 會，每個廠一份 |
| 異常紀錄（`<廠別>.incidents\`） | 會，而且隨時間累積 |

使用者說明（2026-11-17）：廠別會越來越多，知識庫的數量也會一直增加，希望知識庫能定期總結。工程師會跨廠支援，筆電上存有多個廠的資料。

查詢某個廠的問題時，只搜尋共用層加上該廠的資料，所以每次搜尋的範圍只隨該廠自己的資料成長。以 bge-m3 的 1024 維向量估算，5 萬條約 200 MB，逐條比對約數十毫秒（ADR-0022 第 4 點）；數萬條以內效能不需要靠總結解決（Jev 判斷「會成為問題」為 0.37）。總結要解決的是「看得懂整體」與「各廠經驗互通」，不是效能。

## 決策（提議）

0. **原文永遠保留，不以總結取代原文**（Jev 判定「以 LLM 總結取代原文」不適當，值 0.05）。總結與共用條目都是另外加的一層，與 CLAUDE.md 第 12 條「不修改原始紀錄」同樣的精神。
1. **每廠的總結（B）**：
   - **範圍**：每個廠各一份，只用該廠的資料（Jev 0.96）。不做跨廠總結；跨廠的經驗依第 3 點處理。
   - **草稿**：先由 LogTrace **程式統計**：依警報代碼、設備、異常類型計數與排名，列出各項的處置與原文（異常紀錄、知識庫條目）連結；說明文字由工程師補寫。本機 LLM 在現場筆電實測可用後（ADR-0013 第 8 點），再加上 AI 寫的說明草稿，一律標示「AI 推測」，每句附原文出處。
   - **時機**：工程師需要時手動產生；畫面提示距上次產生多久、之後新增幾筆已審核的異常紀錄。
   - **審核**：工程師審核通過後才使用；**只給工程師看**。
   - **保存**：每個廠只保留**最新一份**，記錄產生日期、涵蓋的紀錄範圍與筆數、審核者與日期。
   - 2026-11-17 補充（實作，#168）：
     - **檔案**：廠別設定檔旁的 `<設定檔名>.summary.json`，只放本機、不進 repo；存檔前比對內容，已被別人修改時不覆寫（同 ADR-0016 第 4 點）（使用者決定）。
     - **說明**：整份總結一段，由工程師撰寫；產生新草稿時預先帶入目前的說明（使用者決定；Jev 0.59 信心度不足）。
     - **排名**：每種排名列出全部（使用者決定）。處置以相同寫法（不分全形半形與前後空白）合併並計次。
     - **畫面**：異常紀錄面板的「總結」分頁（使用者決定）；點選排名列出引用的紀錄，再點選看原文。
     - **異常類型**：依警報代碼是否為空推得（「有警報代碼」／「卡住（沒有代碼）」），畫面標示「推得」（Jev 0.77）；ADR-0016 的「異常類型」欄位實作後改用該欄位。
     - **重新產生**：新草稿審核通過前，目前的總結繼續有效；檔案中最多一份已審核加一份草稿（Jev 0.86）。
     - **提示**：顯示目前的總結距今多久、涵蓋筆數、之後新增或改版的已審核紀錄筆數；不另外提示涵蓋的紀錄後來被停用或標示已過時（Jev 0.25）。
     - **審核**：說明空白、產生者與審核者同一人只提醒，確認後仍可通過；沒有審核者時不能通過（同 ADR-0016）。
2. **異常紀錄新增「已過時」狀態**（修改 ADR-0016 第 2 點的狀態清單）：
   - 用於設備已更換、處置方式已改等「當時正確、現在不適用」的紀錄，與「內容有錯而停用」分開。
   - 預設不列入相似查詢與總結，可以勾選顯示。
   - 2026-11-17 補充（使用者決定，#167；待確認 2 已確認）：
     - **誰可以標示**：與審核相同，先不限制，記錄使用者名稱（Jev 0.98）。
     - **理由**：可以不填。
     - **可以標示的狀態**：已審核與修訂中；修訂中標示時，尚未審核的修改不保留（同停用）。
     - **恢復**：同停用，退回草稿、重新審核通過後才回到查詢（Jev 0.80）。
     - **畫面**：異常紀錄面板的查詢分頁加「顯示已過時」勾選，清單中標示已過時（Jev 1.0）。
3. **多廠重複的條目提升到共用層（C）**：
   - **找候選**：兩種都可以：
     - LogTrace 在存有多個廠異常紀錄的電腦上，依相同設備種類、相同警報代碼，或 bge-m3 的現象相似度（ADR-0022）列出候選組，由工程師確認；
     - 工程師自己發現後手動提出。
   - **條件**：至少 **2 個廠**出現。
   - **去除廠別資訊**：
     - 程式自動刪除廠名、設備編號、案件、事件序號與事件內容等欄位。
     - 程式另外掃描現象、原因、處置等自由文字，比對各廠的廠別名稱、Layout 的設備編號與別名，找到時提醒並**擋下審核**（Jev 0.74）。
     - 工程師確認不含廠別資訊後才能審核通過。
   - **格式**：沿用異常紀錄的 JSON 格式與審核流程（草稿、已審核、修訂中、停用、已過時、版本，ADR-0016 第 3 點），存在 `Knowledge\shared\<設備種類>\incidents\`（ADR-0021 第 3 點的共用層），另加「涵蓋廠數」欄（Jev 0.96）。
   - **出處**：共用條目只寫「N 個廠的異常紀錄彙整、審核者、日期」。共用條目對應到各廠原始紀錄編號的對照**另外保存**，只放在有權限的工程師電腦，**不隨共用層發佈**。
   - **來源變更**：來源的廠別紀錄被修訂、停用或標示已過時時，共用條目標示「來源已變更」並**暫停使用**，進入待審核清單，重新審核通過後才恢復。
   - **給誰看**：審核通過的共用條目與已審核的異常紀錄相同，依執行者欄與安全清單（ADR-0014 第 4、5 點），第一線也可以看；也列入「過去相似的異常」（ADR-0016 第 6 點）。
   - **發佈**：由跨廠支援的工程師把共用層帶到各廠的電腦複製。
4. **範圍**：本 ADR 只決定做法。程式實作另外開 ticket，由使用者指示後進行；Claude 不讀取真實的知識庫與異常紀錄（ADR-0021），只寫程式與虛構範例。

## 理由

- 原文保留、總結另成一層，維持「每句事實附出處」（ADR-0013、ADR-0015），總結出錯時仍能回到原文。
- 每廠各自總結，各廠機密不會混在一起；跨廠的經驗只經由去除廠別資訊、經審核的共用條目流通。
- 先以程式統計，不依賴尚未實測的本機 LLM；LLM 可用後再加說明草稿。
- 「已過時」與「停用」分開，事後看得出紀錄是寫錯還是過時，總結與相似查詢也能排除過時的處置。
- 共用條目沿用異常紀錄的格式與流程，審核、版本、待審核清單都可以共用既有的實作（#110）。
- 來源變更時暫停共用條目，避免各廠繼續看到已過時或已停用的處置。

## 考慮過的替代方案與捨棄原因

| 方案 | 捨棄原因 |
|---|---|
| 以 LLM 總結取代原文 | 違反可追溯原則；總結出錯時無法回到原文（Jev 0.05） |
| 不做總結 | 無法看到整體趨勢，各廠經驗不互通（Jev 判斷機率 0.07） |
| 跨廠一份總結 | 各廠機密會混在一起 |
| 總結由本機 LLM 直接產生 | 本機 LLM 尚未在現場筆電實測；改為先程式統計 |
| 總結由 M365 Copilot 產生 | 要把資料帶到辦公室，不符合現場與跨廠支援的使用方式 |
| 固定週期或依筆數自動產生 | 使用者選擇手動產生並提示 |
| 總結給第一線看 | 使用者選擇只給工程師 |
| 只沿用「停用」 | 看不出寫錯還是過時 |
| 工程師依原文重新撰寫共用條目 | 工作量大；改為程式刪除欄位加自由文字掃描，工程師確認 |
| 共用條目直接列出原始紀錄編號 | 編號含異常發生的時間；使用者選擇對照另外保存 |
| 來源變更時共用條目照常使用 | 可能繼續提供已過時的處置 |
| 共用層放在公司共用資料夾 | 使用者選擇由跨廠支援的工程師帶到各廠 |
| 保留每一版總結 | 使用者選擇只保留最新；總結可以從原文重新產生 |
| 共用條目作為對照表 CSV 的列 | 沒有審核、版本與狀態（Jev 0.96 選 JSON） |

## 尚存風險

| 風險 | 影響 | 緩解方式 |
|---|---|---|
| 欄位刪除與自由文字掃描仍漏掉廠別資訊（例如俗稱、Layout 沒有登錄的名稱） | 機密外洩到其他廠 | 擋下審核加上工程師確認；照片或文件欄位目前不做（ADR-0016） |
| 只保留最新一份總結 | 無法查某個時點的總結內容 | 總結可以從原文重新產生；異常紀錄的版本都保留 |
| 由工程師帶到各廠發佈 | 各廠電腦的共用層版本不一致 | 共用層記錄版本與日期，LogTrace 顯示目前使用的版本（待確認 3） |
| 工程師筆電存有多廠資料與對照 | 筆電遺失時影響多個廠 | 公司沒有磁碟加密政策（2026-11-18，待確認 1）：**記為已知風險並接受**；建議工程師向 IT 申請開啟磁碟加密，LogTrace 不另外加密。Windows 有區分使用者登入，但只防止其他帳號登入，硬碟被拆下時無法保護 |
| 本機 LLM 太慢或品質不足 | 總結沒有 AI 說明草稿 | 只用程式統計也能使用 |
| 「兩廠的異常是同一件事」判斷錯誤 | 共用條目誤導其他廠 | 至少 2 廠、工程師審核；第一線只看已審核的條目，並附「N 個廠彙整」 |
| 來源變更時共用條目暫停 | 審核前其他廠暫時看不到 | 待審核清單提示；可以優先審核 |

## 後續驗證方式

以虛構的多廠異常紀錄測試：

- 候選組是否正確（相同設備種類、警報代碼、現象相似度）。
- 欄位刪除與自由文字掃描能否攔下虛構的廠名、設備編號與別名。
- 來源紀錄修訂、停用、標示已過時時，共用條目是否暫停並進入待審核清單。
- 總結的統計（計數、排名、處置連結）是否與原文一致；已過時與停用的紀錄是否排除。
