# ADR-0024：從正常命令學習的卡住比對

- 日期：2026-11-18
- 狀態：**提議中**（做法由使用者決定；實作與虛構資料驗證後才改為已接受）
- 確認者：repo owner（決策內容，2026-11-18）
- 相關 ADR：ADR-0005（世界模型、可能卡住）、ADR-0008（沒有 LOG 的時段）、ADR-0013（知識庫與本機離線 LLM）、ADR-0015（知識檢索）、ADR-0016（異常紀錄）、ADR-0021（電文／代碼對照表）
- 對應 ticket：#192

## 背景

- LogTrace 已經能標示「可能卡住（推估）」（ADR-0005 第 5 點），但只標示、不說明原因。
- 經驗累積（ADR-0016）只從「工程師審核過的異常紀錄」學習；第一次遇到的問題沒有紀錄可以參考。
- 使用者說明（2026-11-18）：希望知識庫最終能回答「某個命令或棧板停在某個位置超過一段時間，主要原因是什麼」，而且不只是看出「一直沒搬」，而是分析出真因，例如「某個值沒有變成應有的值」或「少了某個允許移動的訊號」。做法是從過去同一或相似路線的搬送命令學習。
- 使用者進一步要求（2026-11-18）：建立長期機制，明確定義滿足哪些條件後，就算收集完成、可以判斷「少了哪些資訊，所以沒有繼續搬到下一個位置」；之後分析 LOG 時，依此判斷這次還少了什麼資料或資訊，回報給工程師。

## 決策（提議）

1. **正常流程樣板**：
   - 每次匯入案件時，**自動**統計其中正常完成的搬送命令，累積成每個廠別一份的樣板（使用者決定）。
   - 放在本機（候選：`Plants\<廠別>.flows\`），不進 repo。
   - 只存訊號名稱、角色、出現順序、時間範圍與出現比例，**不存原始 LOG 內容**（ADR-0009）。
   - 「正常完成」：命令有完成回報、期間沒有警報、沒有被標示為「可能卡住」。
   - 同一份 LOG 重複匯入時，不重複計入（Jev 0.77）。
   - 不提供排除案件的功能（使用者決定）。
2. **比對單位是「同一種段落」**（使用者決定）：
   - 同一種設備種類、同一種動作，例如所有 STV 的「站點 → 站點」；不限同一台設備或同一個站點。
   - 因為跨站點與設備，訊號以**角色**記錄，例如「目的站點的置物可」「搬送機的定位」，不記具體的站名或設備編號（Jev 0.79）。
   - 「應該出現的訊號」：在 90%（候選）以上的正常樣本中都出現的訊號（Jev 0.68）。
   - 2026-11-18 補充（本機真實樣本統計後，使用者確認）：**角色依設備種類定義**。
     - 對接設備（Conv）本身沒有訊號，訊號在相鄰的站點上；角色新增「來源相鄰站點」「目的相鄰站點」，相鄰以 Layout 的輸送線連接判斷。
     - RM 段落中途出現的訊號來自與來源、目的地沒有 Layout 關係的站點；「站點編號含有 RM 編號」的規則經驗證對不上。角色不能只靠 Layout 判斷，每種設備要有自己的對應規則。RM 的對應規則**待確認**（待確認 4），確認前 RM 的段落維持「還不能判斷」。
3. **每種段落各自的狀態**：收集中 → 可以判斷 → 需要重新收集。每次匯入後由程式自動重新計算，**不需要工程師確認**（使用者決定）。
4. **「可以判斷」的條件**（全部達成）：
   - ① 正常樣本 ≥ **5 次**（使用者決定）。
   - ② 樣本來自 ≥ **2 個不同案件**（使用者決定；Jev 0.73）。
   - ③ 至少 1 個訊號在 90% 以上的樣本中出現。
   - ④ **自我檢驗**：每一筆正常樣本，和用其餘樣本建立的樣板比對，被誤判為「少了訊號」的比例 ≤ **10%**（使用者決定；Jev 0.73）。
5. **退回**：之後累積時，條件 ④ 的誤報超過 10%（例如設備改造、流程改變），自動退回「需要重新收集」，並在面板提示；樣板以較新的樣本重新建立，細節在實作時決定（Jev 0.74）。
6. **分析時回報三種結果**，每一項附事件出處（Jev 0.82）：
   - **設備少了訊號**：例如「和過去 12 次正常的 STV 站點 → 站點相比，這次沒有出現：目的站點的置物可 ON（正常在派送後 2～5 秒出現）」（範例／虛構）。
   - **LOG 少了資料**：相關模組在那段時間沒有 LOG 或缺檔（ADR-0008），無法判斷；請工程師補收 LOG 後重新匯入。
   - **還不能判斷**：這種段落仍在收集中，顯示目前的樣本數與案件數。
7. **結果是「差異」，不是「真因」**：不寫成「真因是…」（ADR-0015 第 7 點；Jev 判斷「可以直接寫成真因」為 0.08）。工程師確認真因後，可以整理成異常紀錄（ADR-0016），之後直接引用。
8. **第一版只比對訊號 ON／OFF 與出現順序**。「值沒有變成應有的值」**待確認**：先以真實 LOG 在本機確認哪些欄位有記錄值；之後值的意義以電文／代碼對照表（ADR-0021）翻譯。
9. **收集進度畫面**：知識庫面板新增一頁，列出每種段落的狀態、樣本數、案件數與自我檢驗的誤報比例（Jev 0.79）。
10. **先做不需要 LLM 的部分**（使用者決定）：結果顯示在卡住事件的詳細資訊與知識庫面板。本機 LLM 確定後（ADR-0013），再接到對話中，由 LLM 把結果講成話；LLM 不直接讀 LOG 推論真因（Jev 0.86）。
11. **樣板可以在電腦之間匯出、匯入並合併**（2026-11-18 補充，使用者決定）：
    - **保存每一筆樣本的摘要**：段落種類、各角色的訊號與順序、時間間隔、LOG 中原本的站點與設備編號、來源 LOG 檔的雜湊（ADR-0002）；**不存原始 LOG 內容**。彙總的比例、狀態與自我檢驗結果都由摘要重新計算（Jev 判斷「需要保存每筆摘要」為 0.40，信心度不足，由使用者決定）。
    - **合併**：以來源 LOG 檔的雜湊去除重複；條件 ②「不同案件」改以**不同的來源 LOG** 判斷，不以案件名稱判斷，避免同一份 LOG 在兩台電腦建成兩個案件而重複計算。
    - **在 LogTrace 中匯出／匯入**：匯出成一個檔案；匯入前顯示新增幾筆、重複幾筆、哪些段落的狀態會改變，使用者確認後才合併。
    - **版本檢查**：樣板記錄產生它的廠別設定版本；匯入時與本機版本不同就提示，並以本機設定把摘要重新分類、重新做自我檢驗，不直接沿用「可以判斷」（Jev 0.83）。保存原始編號就是為了在別名改變時能重新分類。
    - **視同廠別專屬資料**：只在本機與經授權的工程師電腦之間以檔案傳遞，不進 repo、不上傳外部服務（Jev 0.76）。
    - **與 ADR-0023 的共用層分開**：樣板只屬於單一廠別，不跨廠共用，也不和共用層一起打包。
    - 理由：工程師跨廠支援，多台筆電各自累積一定會發生；保存摘要才能合併，也能在廠別設定改變時重新計算，不必回頭找原始 LOG。同樣的 LOG、設定與程式版本會得到相同結果（Jev 0.87），但各台電腦的 LOG 通常不同，所以帶檔案比重新產生可靠。

## 理由

- 正常完成的命令比異常多得多，第一次遇到的問題也有基準可以比較。
- 「可以判斷」不是自己宣稱的，而是用已經收集到的正常資料實際測過（條件 ④），並且會隨流程改變自動退回。
- 把「LOG 缺資料」和「設備缺訊號」分開，工程師知道該補收 LOG 還是去查設備。
- 程式比對的結果有事件出處，可以檢查；不需要 LLM，現在就能使用，也符合 ADR-0013「事實由程式決定」。

## 考慮過的替代方案與捨棄原因

| 方案 | 捨棄原因 |
|---|---|
| 只從已審核的異常紀錄學習（ADR-0016 原案） | 沒有遇過的問題無法說明 |
| 讓 LLM 直接讀 LOG 推論真因 | 沒有出處、無法檢查，和「事實由程式決定」衝突；本機 LLM 也還沒定 |
| 只比對同一段（同一來源與目的地）或同一台設備 | 樣本累積慢；使用者選擇同一種段落 |
| 工程師指定正常案件，或可以排除案件 | 使用者選擇全自動 |
| 只以樣本數判斷是否收集完成 | 無法證明樣板準確，也無法發現流程改變 |
| 變成「可以判斷」時要工程師確認 | 使用者選擇全自動；結果只寫成差異，風險較低 |
| 補充 ADR-0016，不另開 ADR | 這是新的資料來源與分析方式（Jev 0.89） |
| 每台電腦各自重新累積樣板（2026-11-18） | 要重新收集大量 LOG，結果也可能不同 |
| 樣板只能整份取代（2026-11-18） | 會丟失另一台電腦累積的樣本 |
| 指定一台主要電腦累積（2026-11-18） | 跨廠支援時沒有固定的主要電腦 |
| 直接複製樣板資料夾（2026-11-18） | 沒有版本檢查，也不能合併 |
| 樣板和共用層一起打包（2026-11-18） | 會把廠別資料帶到別的廠 |

## 尚存風險

| 風險 | 影響 | 緩解方式 |
|---|---|---|
| 同一種段落的不同站點，正常訊號本來就不同 | 報出其實不需要的訊號 | 90% 出現比例加上自我檢驗；檢驗不過就不會變成可以判斷 |
| 自動累積時混入沒有被偵測到的異常命令 | 樣板被汙染 | 出現比例門檻；誤報升高時自動退回；日後視情況加排除功能 |
| 少了訊號 X 不等於 X 是真因 | 誤導排查 | 一律寫成差異，真因由工程師確認 |
| 角色對應依賴廠別設定與命令串接（ADR-0005） | 部分模組無法比對 | 說明無法比對的原因，不猜 |
| 門檻（5 次、2 個案件、90%、10%）是初始值 | 太鬆會誤報，太嚴會很久都不能用 | 有真實統計後調整 |
| 值的比對 | 第一版找不到「值不對」的原因 | 待確認；以真實 LOG 確認欄位後補充 |
| 保存每筆樣本摘要讓樣板檔變大（2026-11-18） | 檔案較大 | 每筆只有訊號清單；實際大小待實作後量測 |
| 匯入時誤選別廠的樣板（2026-11-18） | 混入別廠資料 | 匯入時檢查廠別名稱，不同就拒絕 |
| 兩台電腦的廠別設定版本不同（2026-11-18） | 分類結果改變 | 重新分類、重新檢驗並提示 |
| 段落的來源或目的地編號沒有登錄在 Layout（2026-11-18 補充：本機樣本約 2 成） | 無法分類，也無法累積樣本 | 收集進度畫面列出對應不到的段落數；補 Layout 別名（與 #95 待確認的站點編號一起處理） |

## 後續驗證方式

- 虛構情境集：
  - 正常命令中拿掉一個訊號，要能被找出來；正常命令不能被誤報。
  - 相關模組缺 LOG 時，要回報「LOG 少了資料」，不能回報「設備少了訊號」。
  - 樣本或案件不足時，顯示「還不能判斷」與進度。
  - 流程改變後要自動退回。
  - 重複匯入同一份 LOG 不重複計入。
- 真實 LOG：在本機統計各種段落的樣本數、訊號一致程度與自我檢驗結果，只看統計（ADR-0009）。
  - 2026-11-18 第一次統計（1 天、1 個案件；40 筆命令、79 個段落）：
    - 「可能卡住」2 段都與沒有 LOG 的時段重疊，樣本中沒有真正的卡住，**卡住時的比對尚未以真實資料驗證**。
    - STV「站點 → 對接設備」：正常 23 次，6 個訊號在 90% 以上樣本出現，自我檢驗誤報 0%；條件 ①③④ 達成，只差 ②。做法在 STV 上可行。
    - 其他段落種類大多樣本不足，或找不到可比對的訊號（RM，見第 2 點補充）。
    - 約 2 成的段落對應不到 Layout（見尚存風險）。

## 待確認

1. 「值沒有變成應有的值」要比對哪些欄位（以真實 LOG 在本機確認）。
   - 2026-11-18 現況：目前廠別設定的規則只解析到**站點模式**與**站點狀態**兩種值（各 3 種值）；電文的其他欄位值沒有解析規則，要先加規則才能比對。站點模式可以用電文／代碼對照表（ADR-0021）翻譯。
2. 樣板檔的格式與位置。
3. 門檻（5 次、2 個案件、90%、10%）是否需要依真實統計調整。
4. RM 的訊號在哪個站點、該站點與 RM 的關係（第 2 點補充；請工程師說明）。
5. 第 2 天以上的樣本（最好包含真的卡住的時段），用來達成條件 ② 並驗證卡住時的比對。
