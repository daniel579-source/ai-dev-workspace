## 1. 系統邊界與主要責任

### 1.1 系統邊界（初步，待確認）

```
 ┌──────────────────────┐        ┌──────────────────────────────────────┐        ┌──────────┐
 │ 外部（本系統不控制）   │        │ 本系統                               │        │ 使用者    │
 │                      │        │                                      │        │          │
 │ 設備／設備控制電腦     │ LOG 檔 │  收集 → 保存原始檔 → 解析 → 標準化    │  查詢  │ 內部工程師 │
 │ （產生 LOG 檔案）     │ ─────▶ │       → 索引 → 查詢 → 呈現           │ ◀────▶ │          │
 │                      │        │                                      │        │          │
 │ 其他系統？(WMS/WCS)   │ 待確認  │  設備清單、時區／偏差設定、權限、稽核   │        │ 管理者？  │
 └──────────────────────┘        └──────────────────────────────────────┘        └──────────┘
```

### 1.2 本系統責任（候選）

- 取得 LOG 檔案，並在不修改的前提下保存或參照原始檔案。
- 把 LOG 解析並標準化為事件，同時保留原始資訊。
- 提供依時間、設備、關鍵字等條件的查詢。
- 提供跨設備的共同時間軸。
- 維持事件到原始檔案與原始行的追溯關係。
- 管理設備的中繼資料（時區、偏差校正）、權限與稽核紀錄。

### 1.3 不在本系統責任內（候選，對應需求文件 2.2 的非目標）

- 控制設備，或修改設備上的 LOG。
- 即時告警、自動根因分析。
- 設備本身的對時（NTP）管理；本系統只**記錄並呈現**偏差。

## 2. 概念性資料流程

```
[設備 LOG 檔案]
      │ ① 收集（方式待確認：拉取／推送／上傳）
      ▼
[原始檔案保存區]  ← 只寫入、不修改；記錄雜湊值與中繼資料
      │ ② 解析（依設備類型套用解析規則）
      ▼
[解析結果]  ← 包含解析失敗的行
      │ ③ 標準化（時間標準化、時區、偏差校正、欄位對應）
      ▼
[標準化事件]  ← 原始時間＋標準化時間＋原始參照（檔案、行號）
      │ ④ 索引（時間、設備、關鍵字、關聯識別碼）
      ▼
[索引／查詢儲存]
      │ ⑤ 查詢
      ▼
[查詢服務]
      │ ⑥ 呈現
      ▼
[搜尋結果列表／跨設備時間軸／原始紀錄檢視]
```

設計原則（候選，依需求推導）：

- 每一層的輸出都能**回溯到上一層**，最終回到原始檔案。
- 標準化與索引是**衍生資料**，可以從原始檔案重新產生。解析規則或時區設定修正後，可以重建。
- 原始檔案是唯一的真實來源（source of truth）。

## 3. 候選職責分解

| 職責 | 主要工作 | 關鍵議題 | 相關需求 |
|---|---|---|---|
| 收集（Ingestion） | 取得檔案、偵測新檔與輪替、避免重複匯入 | 取得方式、檔案寫入中途是否被讀取、設備端負載 | FR-001、FR-004、Q-004 |
| 原始保存（Raw Storage） | 保存原始檔案、計算雜湊值、記錄中繼資料 | 複製或只參照、壓縮、保存期限 | FR-002、FR-003、NFR-006 |
| 解析（Parsing） | 依格式把行或區塊轉為事件 | 多格式、多行事件、編碼、解析失敗處理、解析規則版本 | FR-010、FR-012、FR-013 |
| 標準化（Normalization） | 時間標準化、時區、偏差校正、欄位對應 | 見第 4 節 | FR-011、FR-014 |
| 索引（Indexing） | 建立時間、設備、全文等索引 | 索引大小、建立速度、重建成本 | FR-020～025、NFR-001～004 |
| 查詢（Query） | 組合條件查詢、排序、分頁 | 穩定排序、大結果集處理 | FR-020～026、NFR-008 |
| 呈現（Presentation） | 結果列表、時間軸、原始紀錄檢視 | 大量事件的呈現與彙總、不確定性標示 | FR-030～042、NFR-003 |
| 管理（Administration） | 設備清單、時區與偏差設定、保存政策 | 設定變更的歷史紀錄 | FR-005、FR-014 |
| 安全與稽核 | 認證、授權、存取紀錄 | 是否整合公司帳號系統 | NFR-012、NFR-013 |

## 4. 時間標準化與設備時鐘偏差

### 4.1 需要區分的時間概念（候選資料概念）

| 概念 | 說明 |
|---|---|
| 原始時間字串 | LOG 中的原文，永遠保留 |
| 解析時間 | 依格式解析出的時間值，可能沒有時區 |
| 時區來源 | LOG 明示／設備設定／推定／未知 |
| 標準化時間 | 換算到統一基準（候選：UTC 儲存、依使用者時區顯示）的時間 |
| 校正後時間 | 標準化時間加上時鐘偏差校正 |
| 時間精度 | 秒／毫秒／微秒等 |
| 檔案內序號 | 事件在原始檔案中的順序，作為次要排序依據 |
| 匯入時間 | 系統取得該資料的時間，用來分析延遲與完整性 |

### 4.2 議題與候選處理方式

| 議題 | 候選處理方式 | 優點 | 缺點／風險 |
|---|---|---|---|
| 時區不一致 | A. 依設備設定時區換算 | 簡單 | 設備設定錯誤或曾經變更時會整段錯位 |
| | B. 以 LOG 中明示的時區優先，沒有時再用設備設定 | 較準確 | 需要每種格式都能判斷 |
| 時鐘偏差 | A. 不校正，只標示「未校正」 | 最單純，不引入錯誤 | 跨設備順序可能誤導 |
| | B. 人工設定每台設備的固定偏差值（含適用期間） | 可控、可稽核 | 需要人力維護；無法處理漂移 |
| | C. 依參考事件（例如設備間交接）自動估計偏差 | 可處理漂移 | 需要可靠的參考事件；演算法複雜；可能估錯 |
| 相同時間戳記 | A. 時間 → 設備 → 檔案內序號 作為穩定排序 | 可重現 | 跨設備的同時事件仍無真實先後，需要在畫面上標示 |
| 跨午夜／缺日期 | 從檔名或檔案時間推得日期 | 可解決只有時間的格式 | 推得錯誤時不易察覺，需要標示「日期為推定」 |

> 時鐘校正方式的選擇取決於 Q-003（對時機制）與 Q-005（容許誤差）。如果偏差遠小於容許誤差，可以只採用 A。

## 5. 容量與效能評估項目

### 5.1 量級估算（假設）

| 項目 | 低端 | 高端 | 備註 |
|---|---|---|---|
| 每日原始資料 | 100 MB | 10 GB | 已確認的量級 |
| 每日行數（假設每行 200 bytes） | 約 50 萬 | 約 5,000 萬 | 平均行長待樣本確認 |
| 保存 30 天的原始資料 | 3 GB | 300 GB | 保存期限待確認 |
| 保存 365 天的原始資料 | 36.5 GB | 3.65 TB | 保存期限待確認 |
| 索引額外空間 | 待評估 | 待評估 | 全文索引可能是原始資料的 0.5～2 倍以上（量級推估，需實測） |

> 兩端相差 100 倍，架構選擇可能因此不同。需要確認的是**常態量**還是**峰值量**，以及成長預期。

### 5.2 必須評估的項目

- [ ] 匯入吞吐量：高端 10 GB／日 ≈ 平均 0.12 MB/s，峰值可能遠高於平均（峰值特性待確認）。
- [ ] 時間區間查詢的回應時間（以時間與設備為主要條件）。
- [ ] 全文關鍵字搜尋的回應時間與索引成本。
- [ ] 時間軸單畫面能承載的事件數，以及超過時的彙總策略。
- [ ] 索引重建時間（解析規則或時區修正後需要重建時）。
- [ ] 儲存成本：原始檔、標準化資料、索引、備份。
- [ ] 同時使用人數下的資源使用量（Q-012）。
- [ ] 收集作業對設備端與網路的負載。

### 5.3 評估方法（建議）

取得真實樣本後，以候選方案做**小規模實測**（僅限評估用途，必須經使用者同意後才執行），量測匯入速度、索引大小與查詢時間，再外推到 10 GB／日。

## 6. 資料保存、備份、權限與稽核

> **已決**（ADR-0009）：不自動刪除、不設保存期限；程式不提供備份，複製案件資料夾即為備份；不另設帳號，依賴作業系統帳號與個人資料夾；不依廠別分權；程式不加密（依賴全碟加密）；只遮罩電話號碼；稽核只記錄匯入、偏移量、套用新版 Layout 等操作。下表保留為當時的評估紀錄。

| 面向 | 待決事項 | 候選方向 |
|---|---|---|
| 原始檔保存 | 保存期限；複製還是參照；是否壓縮 | 原始檔「只寫入一次」；壓縮必須可還原並維持行號參照 |
| 衍生資料保存 | 標準化資料與索引的保存期限可以短於原始檔嗎？ | 衍生資料可以重建，期限可以分開設定 |
| 保存期限到期 | 到期後的處理方式；與可追溯性的衝突 | 必須有明確政策；刪除須經授權並留下紀錄；**本系統不得自行刪除原始 LOG，除非政策明確授權** |
| 備份 | RPO／RTO；備份範圍 | 至少備份原始檔與設定（設備清單、時區、偏差、解析規則） |
| 權限 | 是否依設備或廠區分權；是否整合公司帳號 | 待 Q-010、Q-011 |
| 稽核 | 記錄查詢、匯出、設定變更、偏差校正值變更 | 設定變更必須留存歷史，以便解釋過去的查詢結果 |
| 敏感資訊 | LOG 是否含個資或機密 | 待 Q-014；可能需要遮罩或權限控管 |

## 7. 候選架構方案

> **已決**（ADR-0011，待實測）：以 SQLite 為主要儲存的混合方案（接近下列方案 A 加上掃描）。下列內容保留為當時的評估紀錄。

> 以下三案都是**候選方案**，用來比較取捨，不是最終設計。技術名稱只是舉例，表示「這一類」做法。

### 候選方案 A：檔案為主＋輕量索引

- **概念**：原始檔案保留在檔案系統；另外建立以時間與設備為主的輕量索引；關鍵字搜尋直接掃描對應時間範圍內的檔案。
- **優點**：架構最簡單；儲存成本低；原始檔案就是查詢來源，追溯最直接。
- **缺點**：大範圍關鍵字搜尋會很慢；高端資料量下的效能存疑；跨設備時間軸需要即時合併多個檔案。
- **適用條件**：資料量偏向低端，或查詢通常限定在短時間範圍與少數設備。

### 候選方案 B：關聯式或時序資料庫儲存標準化事件

- **概念**：解析後的標準化事件寫入資料庫（例如關聯式資料庫或時序資料庫類別），以時間與設備建立索引；原始檔另外保存，事件帶有原始參照。
- **優點**：時間區間與結構化欄位查詢快；排序規則容易控制；交易與一致性較好。
- **缺點**：全文關鍵字搜尋能力依產品而定，可能不足；高端資料量下的儲存與索引成本需要評估；需要定義資料結構，格式多變時調整成本較高。
- **適用條件**：LOG 結構化程度高，查詢以時間、設備、錯誤碼為主。

### 候選方案 C：全文搜尋引擎／LOG 分析平台

- **概念**：標準化事件寫入全文搜尋引擎或 LOG 平台類別的產品，提供全文與時間範圍查詢；原始檔另外保存。
- **優點**：關鍵字搜尋強；處理大量 LOG 的能力成熟；部分產品內建時間軸視覺化。
- **缺點**：維運複雜度與資源需求高；索引空間大；現成視覺化未必滿足「跨設備時間軸＋追溯原始行」的特定需求；授權與成本需要評估；**若為外部 SaaS，必須確認是否符合資料不外送的原則**。
- **適用條件**：資料量偏向高端，且關鍵字搜尋是主要使用方式。

### 候選方案 D：混合方案

- **概念**：結構化欄位用 B 類儲存，全文搜尋用 C 類或檔案掃描，兩者以事件識別關聯。
- **優點**：兼顧兩種查詢型態。
- **缺點**：兩套資料要保持一致，複雜度最高。

### 比較摘要（初步，待實測驗證）

| 評估面向 | A 檔案為主 | B 資料庫 | C 搜尋引擎 | D 混合 |
|---|---|---|---|---|
| 時間區間查詢 | 中 | 佳 | 佳 | 佳 |
| 關鍵字搜尋 | 差～中 | 差～中 | 佳 | 佳 |
| 原始追溯 | 佳 | 佳（需要參照設計） | 佳（需要參照設計） | 佳 |
| 高端資料量適應性 | 差 | 中 | 佳 | 佳 |
| 維運複雜度 | 低 | 中 | 高 | 高 |
| 格式變動適應性 | 佳 | 中 | 中～佳 | 中 |

> 評等為依一般經驗的**初步判斷**，必須以真實樣本實測後修正。

### 呈現層候選

| 候選 | 優點 | 缺點 |

## 9. 作出架構決策所需的資訊

依優先順序排列：

1. **真實（去識別化）LOG 樣本**：每種設備至少一份，包含跨午夜、檔案輪替、錯誤情況的樣本（Q-001）。
2. **時間資訊**：時間格式、時區、精度、對時機制、已知偏差（Q-002、Q-003、Q-005）。
3. **收集環境**：LOG 存放位置、網路拓樸、能否從設備端讀取（Q-004）。
4. **部署限制**：內網或外網、既有伺服器、IT 規範、指定或禁用的技術、團隊技能（Q-011）。
5. **資料量細節**：常態量與峰值量、設備數量、成長預期（Q-001、5.1）。
6. **保存與合規**：保存期限、稽核要求、敏感資訊（Q-009、Q-010、Q-014）。
7. **使用型態**：同時使用人數、常用查詢區間、回應時間期望、匯入延遲容忍度（Q-008、Q-012、Q-013）。

```markdown
- 理由：
- 考慮過的替代方案與捨棄原因：
- 尚存風險：
- 後續驗證方式：
```

## 11. 主要風險（初步）

| 編號 | 風險 | 影響 | 緩解方向（候選） |
|---|---|---|---|
| R-001 | 未取得真實樣本就開始設計 | 解析與標準化設計需要大幅重做 | 先取得樣本再決定架構 |
| R-002 | 時區或時鐘偏差未正確處理 | 時間軸順序錯誤，誤導故障判斷 | 保留原始時間；標示不確定性；設定可稽核 |
| R-003 | 資料量落在高端，候選方案效能不足 | 查詢太慢，無法使用 | 以樣本實測後再選型 |
| R-004 | 保存政策與可追溯性衝突 | 舊事件無法追溯原始行 | 保存政策與追溯需求一起設計 |
| R-005 | 真實 LOG 外流至未核准的外部服務 | 資訊安全事件 | 遵守 CLAUDE.md 第 3.6 節；評估 SaaS 時特別審查 |
| R-006 | 格式種類多且常變動 | 解析維護成本高 | 解析規則與核心分離；解析失敗不丟棄 |
