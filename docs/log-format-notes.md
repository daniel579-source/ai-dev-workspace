> **重要原則**
> 1. 本文件**不得虛構實際設備格式**。樣本無法證實的內容一律標示「待確認」或「假設」。
> 2. 本文件只寫**去識別化**的描述。客戶名稱、IP、電話、物料編號、單號、資料表名稱一律不寫出；範例行一律為**虛構**並標示「範例／虛構」。
> 3. 真實 LOG **不得**上傳到未經核准的外部服務（含線上格式轉換、外部 AI 服務、GitHub issue）。
> 4. 本次樣本共用同一種容器格式，因此共通部分寫在第 2 節，各 LOG 種類只在第 3 節記錄差異。新類型 LOG 若格式不同，使用附錄 A 的完整調查表。

## 2. 共通格式（全部 13 種 LOG）

以下內容由樣本統計得出，13 種 LOG 全部一致，除非另行註明。

### 2.1 目錄與檔名

| 項目 | 內容 | 狀態 |
|---|---|---|
| 目錄結構 | `<yyyyMMdd>/<來源>-<yyyy-MM-dd>/<Logger>.txt`；輪替檔在 `<來源>-<日期>/archives/` | 樣本 |
| 檔名規則 | 現行檔為 `<Logger名稱>.txt`，**不含日期**；日期只出現在上層資料夾 | 樣本 |
| 輪替檔名 | `<Logger名稱>_<yyyy-MM-dd HH_mm_ss.ffff>.txt`；檔名時間＝**新檔第一筆紀錄的時間** | 樣本（僅 1 例） |
| 同名 Logger 跨來源 | `DBUPDATE_LOG` 同時出現在 EXE、PLC、Server，內容不同 → **檔名不能當唯一識別，必須搭配來源** | 樣本 |
| 來源端保留期限 | PLC 端有紀錄顯示會刪除超過 90 天的 LOG 資料夾 | 樣本（僅 PLC） |

### 2.2 紀錄格式

| 項目 | 內容 | 狀態 |
|---|---|---|
| 格式類型 | 純文字；每筆紀錄以 `時間 \| 等級 \| Logger \| 訊息` 開頭，分隔符為 ` \| `（空白、直線、空白） | 樣本 |
| 紀錄結尾 | 多數紀錄以「訊息＋兩個空白＋CRLF」結束，**後面再接一個空行**；空行不屬於任何事件 | 樣本 |
| 多行事件 | **存在**。不以時間戳記開頭的行屬於前一筆紀錄的延續（stack trace、HTTP 標頭與內文、SQL） | 樣本 |
| 換行字元 | 以 CRLF 為主；部分檔案混有少量單獨 LF（出現在多行內容中） | 樣本 |
| BOM | 無 | 樣本 |
| 等級 | 只見 `DEBUG` 與 `INFO`；**樣本中沒有 WARN／ERROR**，錯誤以例外文字或訊息內容呈現 | 樣本 |
| Logger 欄位 | 與檔名相同 | 樣本 |
| 壓縮 | 交付時整天打包為一個 7z；個別檔案未壓縮 | 樣本 |
| 官方格式文件 | 無。格式外觀類似 .NET 常見的 LOG 函式庫輸出 | 假設 |

### 2.3 文字編碼

| 項目 | 內容 | 狀態 |
|---|---|---|
| 編碼 | **混用**：EXE 全部與 Server 的 WCSCMD 為 UTF-8；PLC 全部與 Server 其他檔案為 Big5 | 樣本 |
| 判斷方式 | 檔案沒有 BOM，編碼無法從檔頭得知，只能用試解碼判斷 | 樣本 |
| 同一台電腦內也混用 | Server 同時有 UTF-8 與 Big5 檔案 | 樣本 |

### 2.4 時間戳記

| 項目 | 內容 | 狀態 |
|---|---|---|
| 格式 | `yyyy-MM-dd HH:mm:ss.ffff`（例：`2025-01-01 08:00:00.1234`，範例／虛構） | 樣本 |
| 是否包含日期 | 是 | 樣本 |
| 精度 | 小數 4 位，即 **100 微秒**；13 種 LOG 全部相同 | 樣本 |
| 時區 | **LOG 未標示**；也沒有 UTC 偏移 | 樣本 |
| 時區值 | 未知。**假設**為設備所在地當地時間 | 假設 |
| 時間代表的意義 | 寫入 LOG 的時間（非事件發生時間） | 假設 |
| 對時機制 | 未知 | 待確認 |
| 同一時間戳記多筆 | **常見**。相鄰紀錄時間相同的比例：PLCLOG 約 30%、EXEDebug 約 42%、BCR_LOG 約 20% | 樣本 |
| 行序是否等於時間順序 | **否**。PLCLOG 有 6 處、WebServiceLOG 有 2 處時間倒退，最大倒退約 16 ms 與 34 ms；其他檔案未見倒退 | 樣本 |

## 3. 各 LOG 種類

範例行均為**範例／虛構**，只示意結構。

### LF-001～LF-005：EXE

| 編號 | Logger | 編碼 | 事件數／大小 | 多行 | 內容 | 可見識別碼 |
|---|---|---|---|---|---|---|
| LF-001 | WebServiceLOG | UTF-8 | 1,510／1.6 MB | 是（HTTP 標頭與 JSON 內文） | 與上位系統之間的 HTTP 收發：收到任務（POST）、回應狀態碼；另有簡訊通知 API 的收發，內含**告警文字與電話號碼** | 命令編號、站點、IP |
| LF-002 | EEWLOG | UTF-8 | 1,812／0.3 MB | 是（HTTP 標頭） | 外部主機定期呼叫的健康檢查（Ping），約每分鐘數次，**從 00:00 起連續不斷** | IP |
| LF-003 | EXEDebug | UTF-8 | 543／0.1 MB | 否 | 任務處理流程的中文敘述：寫入庫存、完成回報上位系統（含站點、設備、命令編號，部分為 JSON） | 命令編號、站點、設備、客戶物料資訊 |
| LF-004 | DBUPDATE_LOG | UTF-8 | 1,154／0.8 MB | 少量 | 寫入資料庫的完整 SQL（INSERT／UPDATE） | 命令編號、站點、設備 |
| LF-005 | DBLOG | UTF-8 | 35／0.06 MB | **是（每筆都有 stack trace，約 12 行）** | 資料庫存取的例外；樣本中 35 筆都是同一種型別轉換例外 | — |

範例／虛構：
```
2025-01-01 08:00:00.1234 | DEBUG | EXEDebug | SubmitCompleted,StationNo=A-99,RMC_ID=XXXX99,CMD_NO=00099999
```

### LF-006～LF-010：PLC

| 編號 | Logger | 編碼 | 事件數／大小 | 多行 | 內容 | 可見識別碼 |
|---|---|---|---|---|---|---|
| LF-006 | PLCLOG | Big5 | 6,532／0.8 MB | 否 | 每筆以 `[站點][處理名稱] =>` 開頭。處理名稱有：站點狀態變化（約 2,700 筆）、條碼入庫要求（約 2,000 筆）、出庫循環、RFID 入庫要求、卸貨、任務回應、寫入資料等 | 站點、設備、命令編號、棧板命令、物料 |
| LF-007 | PLCExecTimeLOG | Big5 | 139／0.02 MB | 否 | PLC 命令處理的執行紀錄，欄位以 ` \| ` 分隔：PLC ID、站點、命令編號、命令類型、設備、訊息（如「到達」） | PLC ID、站點、命令編號、設備 |
| LF-008 | BCR_LOG | Big5 | 3,075／0.4 MB | 否 | 條碼讀取器的 TCP 連線、開關讀取、收到資料 | 站點、IP |
| LF-009 | DBUPDATE_LOG | Big5 | 977／0.7 MB | 少量 | PLC 端寫入資料庫的 SQL，前面帶有觸發的處理名稱 | 站點、設備、命令編號、物料 |
| LF-010 | WMSDebug | Big5 | 1 | 否 | 刪除 90 天前 LOG 資料夾的紀錄 | — |

**站點狀態變化（PLCLOG）**的格式為 `[站點][Station_Status_Change] => <狀態名稱> = ON／OFF`，或 `=> 命令編號 = <8 位數字>`。樣本中的狀態名稱依筆數：在席（976）、取物可、下定位、上定位、置物可、入庫要求、WT 回報要求、順轉定位、逆轉定位、夾臂退回、夾臂伸出等。這些是 **ON／OFF 的位元狀態**，沒有座標。

範例／虛構：
```
2025-01-01 08:00:00.1234 | DEBUG | PLCLOG | [A-99][Station_Status_Change] => 在席 = ON
2025-01-01 08:00:00.1234 | DEBUG | PLCLOG | [A-99-XXXX99][Station_Status_Change] => 命令編號 = 00099999
```

## 5. 觀察與對設計的影響

| 編號 | 觀察 | 對設計的影響 | 狀態 |
|---|---|---|---|
| O-001 | 13 種 LOG 共用一種容器格式 | 可以用一個共通的「紀錄切分＋時間解析」層處理全部，各 LOG 種類只需要訊息內容的解析規則 | 樣本 |
| O-002 | 編碼混用且沒有 BOM，同一台電腦內也混用 | 編碼必須能依檔案設定；自動偵測只能當輔助；解碼失敗不能丟資料 | 樣本 |
| O-003 | 多行事件存在，且每筆紀錄後有空行 | 紀錄邊界以「行首時間戳記」判定；空行要排除；原始行號要記錄事件的**起訖行** | 樣本 |
| O-004 | 時間無時區、精度 100 μs | 必須保留原始時間字串；時區按來源設定 | 樣本 |
| O-005 | 同一時間戳記非常常見（最高約 42%） | 排序必須有穩定的次序鍵（例如來源、檔案、行號），不能只靠時間 | 樣本 |
| O-006 | 同一檔案內時間會倒退（最多約 34 ms） | 「檔案內行序」與「時間順序」不一致；要決定排序依哪一個，並保留兩者 | 樣本 |
| O-007 | 檔案依某種條件輪替，封存檔約 10 MB | **假設**為依大小輪替（約 10 MB）；同一 Logger 會跨多個檔案，匯入時要依時間接續 | 假設（僅 1 例） |
| O-008 | 多數 LOG 在 02:10 至 06:53 之間沒有紀錄，但 EEWLOG（健康檢查）與 Server DBUPDATE_LOG 持續有紀錄 | 這段空白較可能是**沒有作業**而不是 LOG 遺失；資料缺口偵測（FR-037）要能區分「沒有活動」與「沒有紀錄」 | 假設 |
| O-009 | 樣本結束於約 14:51，不是完整一天 | 「一天份」的打包時間點不一定在午夜；匯入要處理部分日期 | 樣本 |
| O-010 | 以「命令編號在各來源第一次出現的時間」比對，PLC 比 EXE 早約 15～16 秒（中位數），Server 比 EXE 晚約 78 秒（中位數），且差距不固定 | 可能是**時鐘偏差**，也可能是**處理流程本身的先後與延遲**；單憑此資料無法區分。時間策略決策需要釐清命令的實際流向 | 待確認 |
| O-011 | PLC 只記錄站點層級的 ON／OFF 狀態與命令編號，沒有座標 | 回放為站點層級；設備與貨物的位置要從站點狀態與命令推導 | 樣本 |
| O-012 | 站點有兩套編號：文字型（`A-nn`）與數字型 | Layout 必須能把兩套編號對應到同一個站點，或確認兩者是不同層級的東西 | 待確認 |
| O-013 | 等級幾乎都是 DEBUG，沒有 ERROR | 「異常」不能靠等級判定，要靠訊息內容（例外、告警文字、特定狀態） | 樣本 |
| O-014 | 告警文字出現在簡訊通知的內容中（例如設備門開啟異常） | 可能是判定「異常熱區」的重要來源之一 | 樣本 |
| O-015 | 含敏感資訊：內網 IP、客戶名稱、物料、單號、**電話號碼** | 系統內是否遮罩、誰能看，需要在敏感資訊決策中處理 | 樣本 |
| O-016 | 樣本一天約 20 MB，遠低於需求寫的 100 MB～10 GB | 需求量級可能是多倉庫、多天或其他設備的總和；容量估算要再確認 | 待確認 |
