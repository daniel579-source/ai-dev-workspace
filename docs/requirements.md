## 1. 專案背景與問題陳述

### 1.1 背景

公司的自動化倉儲系統由多台設備組成（實際設備種類與數量**待確認**），各設備或其控制電腦會產生 LOG 檔案。設備發生異常時，工程師需要從這些 LOG 找出原因。

### 1.2 問題陳述（依初步需求整理，細節待確認）

- LOG 分散在不同設備或電腦上，格式可能各不相同（**待確認**），難以一起查看。
- 異常往往牽涉多台設備，工程師需要人工比對不同來源的時間，才能拼出事件順序。
- 各設備的時間戳記可能採用不同時區或格式，時鐘也可能不同步（**待確認**），人工比對容易出錯。
- 每日資料量估計達 100 MB 至 10 GB，人工翻閱很沒有效率。
- 結果：故障排查耗時，也難以還原「當時到底發生了什麼」。

## 2. 專案目標與非目標

### 2.1 目標（已確認）

- G-1：讓工程師能依時間、設備、關鍵字搜尋 LOG。
- G-2：將多台設備的事件整合到共同時間軸。
- G-3：讓工程師能查看指定時間區間內的事件。
- G-4：協助工程師重建特定時間的事件順序與設備狀態。
- G-5：以時間為基準，盡可能重現當時情況，並縮短故障排查時間。

### 2.2 非目標（第一階段暫不處理；**待確認**是否同意）

- NG-1：即時監控與即時告警。
- NG-2：自動判斷故障根因（AI／規則引擎的根因分析）。
- NG-3：控制或回寫設備，也就是不對設備下任何指令。
- NG-4：取代既有的 WMS／WCS／MES 系統。
- NG-5：修改、清洗或刪除原始 LOG。
- NG-6：對公司外部使用者開放。

> 上述非目標是為了界定範圍而提出的**假設**。如果其中有第一階段必須做的項目，需要重新評估範圍與架構。

## 3. 使用者角色與典型使用情境

### 3.1 使用者角色

| 角色 | 說明 | 狀態 |
|---|---|---|
| 現場／維護工程師 | 處理設備異常，需要快速查詢事件順序 | 已確認（「公司內部工程師」） |
| 系統／控制工程師 | 分析跨設備的交互問題、時序問題 | 假設 |
| 系統管理者 | 管理 LOG 來源、設備清單、保存政策與帳號權限 | 假設 |

> 工程師是否要再細分角色、各角色能看到哪些設備的 LOG，都**待確認**（見 Q-010）。

### 3.2 典型使用情境（依目標推導，待確認）

- **UC-1 異常時間點回溯**：工程師得知「某時刻某設備停機」，查看該時刻前後數分鐘所有相關設備的事件。
- **UC-2 關鍵字／錯誤碼搜尋**：工程師用錯誤碼或訊息關鍵字，找出它在一段期間內出現的所有時間點與設備。
- **UC-3 跨設備關聯追蹤**：工程師用任務編號或工件編號（若存在，**待確認**）追蹤一件貨物在不同設備間的流轉過程。
- **UC-4 狀態重建**：工程師想知道某時刻某設備處於什麼狀態，例如運轉中、待機或異常（狀態是否能從 LOG 推得，**待確認**）。
- **UC-5 回到原始紀錄**：工程師對時間軸上的某事件存疑，跳到原始檔案的原始行，查看上下文。

## 5. 時間與資料品質相關需求分析

本節只分析問題與影響，**不決定實作方式**。候選做法列在 `docs/architecture.md`。

### 5.1 不同時區或格式的時間戳記

- **問題**：設備可能使用不同時區（UTC、當地時間、未標示），格式也可能不同（ISO 8601、自訂格式、Unix epoch、只有時間沒有日期等）。
- **影響**：
  - 未標示時區的時間只能靠設備設定推定，推定錯誤會讓跨設備排序整段錯位（例如差 8 小時）。
  - 如果有日光節約時間，會出現重複或不存在的時刻（台灣目前沒有實施，但設備是否設定在其他時區，**待確認**）。
  - 只有時間、沒有日期的 LOG，必須從檔名或檔案時間推得日期，跨午夜時容易出錯。
- **需求方向**：保留原始時間字串；標準化時間要記錄「時區來源」（LOG 明示、設備設定、推定）；解析規則要能依設備個別設定。
- **待確認**：Q-002、Q-003。

### 5.2 設備時鐘不完全同步

- **問題**：各設備時鐘可能有固定偏差或漂移，NTP 同步狀況不明（**待確認**）。
- **影響**：
  - 跨設備的因果順序可能被誤判。例如 A 設備的錯誤其實發生在 B 設備之後，但看起來在前。
  - 偏差若隨時間漂移，單一校正值無法套用整段期間。
  - 校正需要參考依據，例如同一任務在兩台設備的交接事件、或已知同步的參考時鐘；目前不知道是否存在這類依據。
- **需求方向**：
  - 能記錄每台設備的偏差資訊（數值、適用期間、來源、確認者）。
  - 校正後的時間與原始時間並存，使用者可以選擇顯示哪一種。
  - 偏差量級在可接受誤差內時，可能不需要校正；容許誤差**待確認**（Q-005）。

### 5.3 多筆事件具有相同時間戳記

- **問題**：時間精度不足（例如只到秒）或事件密集時，會有多筆事件時間相同。
- **影響**：只依時間排序會讓順序不穩定，每次查詢結果的順序可能不同，造成誤導。
- **需求方向**：
  - 排序必須穩定且可重現。同一設備內，可依原始檔案中的順序作為次要排序依據（**假設**：檔案內的順序等同發生順序，待確認）。
  - 不同設備之間時間相同時，系統無法得知真實先後，應在畫面上標示「順序不確定」，不能暗示有先後關係。
  - 時間精度要記錄下來，例如「精度：秒」，讓使用者知道排序的可信度。

### 5.4 LOG 缺漏、重複、延遲產生、跨檔案分割

| 情況 | 可能原因（推測） | 影響 | 需求方向 |
|---|---|---|---|
| 缺漏 | 設備斷電、磁碟滿、輪替遺失、收集失敗 | 時間軸有空白，可能被誤讀為「沒發生事」 | 偵測並標示資料缺口（FR-037）；記錄收集狀態 |
| 重複 | 重複收集、同一檔案被複製、設備重送 | 事件被重複計算，順序混亂 | 檔案層級去重（FR-004）；事件層級去重規則**待確認**，因為相同內容也可能是真實的重複事件 |
| 延遲產生 | 設備先暫存再寫出、批次上傳 | 寫入時間 ≠ 事件發生時間；查詢時資料還不完整 | 區分「事件時間」與「寫入／匯入時間」；標示資料最後更新時間 |
| 跨檔案分割 | 檔案輪替（依大小或日期）、一個事件被切到兩個檔案 | 事件被截斷；同一時段的資料分散在多個檔案 | 能依設備把多個檔案視為連續資料流；處理被切斷的多行事件 |

> 上述「可能原因」都是**推測**，要等取得真實樣本與收集環境資訊後才能確認（見 `docs/log-format-notes.md`）。

### 5.5 從時間軸追溯到原始檔案與原始行

- **需求**：每筆標準化事件都必須帶有一組足以定位原始紀錄的參照，概念上至少包括：來源設備、原始檔案識別（路徑或雜湊值）、行號或位元組位移、原始文字。
- **影響**：
  - 原始檔案不能被修改或刪除，否則參照會失效。保存政策必須和這點一致。
  - 如果原始檔案經過壓縮、搬移或輪替，參照方式要能承受這些變動。
  - 多行事件需要記錄起訖行。
- **未決**：原始檔案由本系統保存一份副本，還是只參照原位置（見 `docs/architecture.md`）。

### 5.6 每日資料量可能達 10 GB

- **規模估算（假設，僅供量級參考）**：以每行平均 200 bytes 計算，10 GB／日約為 5,000 萬行／日；保存 90 天約為 900 GB 原始資料、45 億行。實際平均行長、保存期間與成長率都**待確認**。
- **必須在架構階段評估的項目**：
  - 查詢效能：時間區間查詢、關鍵字全文搜尋的回應時間目標（NFR-001～003）。
  - 資料索引：哪些欄位要建索引；全文索引所需空間可能和原始資料同量級甚至更大。
  - 保存政策：原始檔案、標準化資料、索引各要保存多久。
  - 資源使用：儲存空間、記憶體、CPU、匯入時對設備端或網路的負載。
  - 匯入延遲：LOG 產生後多久要能被查詢到（Q-008）。

## 7. 使用流程

> 以下流程描述「使用者要完成什麼」，不規定畫面設計或技術實作。

### 7.1 以時間區間查詢 LOG

1. 工程師輸入時間區間（起訖時間）。
   - 待確認：輸入的時間以哪個時區解讀（預設使用者所在時區？），以及是否支援「某時刻 ± N 分鐘」的輸入方式。
2. （選填）選擇一台或多台設備。
3. （選填）輸入關鍵字、事件等級、錯誤碼等條件。
4. 系統回傳符合條件的事件列表：
   - 依標準化時間排序，同一時間的事件依 5.3 的規則處理。
   - 每筆事件顯示：標準化時間、原始時間、設備、等級（若有）、訊息摘要。
   - 標示時間的不確定性（經過校正、時區是推定的等）。
5. 結果過多時，系統提示縮小範圍或分頁瀏覽（上限與處理方式待確認）。
6. 工程師可以：
   - 點選某事件，追溯到原始紀錄（見 7.3）；
   - 切換到時間軸檢視（見 7.2）；
   - 調整條件後重新查詢。

### 7.2 跨設備事件時間軸

1. 工程師用以下任一方式指定時間區間：
   - 直接輸入時間區間；
   - 從搜尋結果中選一個事件，以它為中心展開前後 N 分鐘；
   - 用關聯識別碼（若存在）找出相關事件的時間範圍。
2. 選擇要並列比較的設備（預設：有事件的設備，或與關聯識別碼相關的設備；待確認）。
3. 系統把各設備的事件放到共同時間軸上：
   - 各設備可區分，例如分軌顯示；
   - 時間採同一基準（標準化時間或校正後時間，使用者可以切換；待確認）；
   - 標示資料缺口與順序不確定的事件。
4. 工程師縮放或平移時間軸，觀察事件的先後與密度。
5. 工程師選取某時刻，系統顯示該時刻各設備最近的事件與推定狀態（若能推定，見 FR-035、Q-007）。
6. 工程師點選事件，追溯原始紀錄。

### 7.3 搜尋結果與原始 LOG 的追溯關係

```
時間軸事件／搜尋結果
   │  帶有：事件識別、標準化時間、處理紀錄
   ▼
標準化事件紀錄
   │  參照：來源設備、原始檔案識別、行號／位移、原始文字
   ▼
原始 LOG 檔案（未修改）
   │  驗證：檔案雜湊值與匯入時紀錄一致
   ▼
原始行及前後文
```

- 工程師點選事件後，應能看到：
  1. 原始檔案的識別資訊（設備、檔名、路徑）；
  2. 原始行號與原始文字（多行事件顯示起訖行）；
  3. 前後文；
  4. 該事件經過的處理：時區轉換、時鐘校正、多行合併、解析規則版本。
- 如果原始檔案已依保存政策移除，系統必須明確告知，不能顯示錯誤的內容。

## 9. 假設清單

| 編號 | 假設 | 被推翻時的影響 |
|---|---|---|
| A-001 | LOG 是文字檔，以行為基本單位 | 若有二進位格式或資料庫匯出，解析與追溯方式都要重新設計 |
| A-002 | 同一個 LOG 檔案中，行的順序等於事件的發生順序 | 同一時間戳記的排序規則就不可靠 |
| A-003 | 原始 LOG 能以某種方式複製或讀取到本系統可存取的位置 | 收集機制要重新設計，可能需要設備端代理程式 |
| A-004 | 使用者都是內部工程師，在公司網路內使用 | 安全與部署需求會大幅改變 |
| A-005 | 第一階段不需要即時性，可接受批次匯入 | 若需要近即時，架構複雜度會明顯提高 |

## 10. 待確認問題與優先順序

> 優先順序：**P1** = 阻擋架構決策，必須最先確認；**P2** = 影響功能設計；**P3** = 可以稍後確認。

| 編號 | 優先 | 問題 | 對設計的影響 |
|---|---|---|---|
| Q-001 | P1 | 有哪些設備種類與數量？每種設備的 LOG 格式為何？能否提供去識別化樣本？ | 決定解析器的數量與複雜度；沒有樣本就無法驗證任何設計 |
| Q-002 | P1 | 各設備的時間戳記格式、時區、精度為何？LOG 中是否標明時區？ | 決定能否正確跨設備排序；影響標準化設計 |
| Q-003 | P1 | 設備與電腦是否有 NTP 或其他對時機制？已知的時鐘偏差量級為何？ | 決定是否需要時鐘校正機制，以及校正的依據 |
| Q-004 | P1 | LOG 檔案存放在哪裡？本系統要如何取得（網路分享、上傳、代理程式、人工複製）？ | 決定收集架構、部署位置與網路需求 |
| Q-005 | P1 | 跨設備排序的容許誤差是多少（例如 1 秒、100 毫秒）？ | 決定時間精度要求與校正機制的必要性 |
| Q-006 | P2 | 是否有任務編號、工件編號、條碼等跨設備的關聯識別碼？ | 決定能否做關聯追蹤（UC-3） |
| Q-007 | P2 | 「設備狀態」指什麼？能從 LOG 直接得到，還是要從事件推導？有沒有狀態定義表？ | 決定 FR-035 的可行性與做法 |
| Q-008 | P1 | LOG 產生後多久要能查到？批次（每日或每小時）是否可接受？ | 決定匯入架構與複雜度 |
| Q-009 | P1 | 原始 LOG 與衍生資料要保存多久？設備端是否會自行刪除舊 LOG？ | 決定儲存容量與保存架構；影響可追溯性 |
| Q-010 | P2 | 權限是否需要依設備、產線或廠區區分？是否需要稽核紀錄？ | 決定權限模型與稽核設計 |
| Q-011 | P1 | 部署環境限制：是否只能在工廠內網？有沒有既有伺服器、IT 規範或指定技術？ | 決定候選架構的可行範圍 |
| Q-012 | P2 | 同時使用的人數大約多少？ | 影響效能與資源規劃 |
| Q-013 | P2 | 查詢回應時間的期望為何？最常查詢的時間區間多長？ | 決定索引策略與 NFR-001～003 的目標 |
| Q-014 | P2 | LOG 是否含有敏感資訊（人員帳號、客戶資料、網路位址等）？需要遮罩嗎？ | 影響匯入流程、權限與範例資料處理 |
| Q-015 | P3 | 是否需要匯出或分享查詢結果？格式為何？ | 決定 FR-050、FR-051 是否納入第一階段 |
| Q-016 | P3 | 第 2.2 節的非目標是否都同意？ | 確認範圍邊界 |
| Q-017 | P2 | 是否需要整合其他系統的資料（WMS、WCS、PLC 等）？ | 影響資料來源範圍與系統邊界 |
| Q-018 | P3 | 使用者介面偏好：Web 瀏覽器、桌面應用程式，或兩者皆可？ | 影響前端技術評估 |
