# 異常紀錄雛形（ADR-0016、#107）

> **雛形・可丟棄**。只放在 `prototype/incident-records` 分支，不合併進 main。所有資料都是**範例／虛構**。

開啟方式：直接用瀏覽器打開 `incident-records-prototype.html`，不需要安裝任何東西。

## 要回答的問題

1. 異常紀錄的候選欄位夠不夠用？包括從案件產生的紀錄，以及從過去維修紀錄整理的紀錄。
2. 「草稿 → 已審核 → 停用」的流程合不合理？審核時「AI 推測」要怎麼處理？已審核的紀錄還能改嗎？
3. 查詢「過去相似的異常」時，工程師和第一線各看到什麼？

## 雛形採用的規則（第 2 版，2026-11-13 依使用者回覆修改）

| 項目 | 雛形的做法 | 依據 |
|---|---|---|
| 欄位 | 來源（案件／維修紀錄）、現象、開始、結束、廠別、案件、相關事件、警報代碼、相關設備、**停機時間、處理人、照片或文件**、原因、處置、執行者、結果；另有撰寫者、停用原因、版本、修訂經過、操作經過 | 使用者：欄位加停機時間、處理人、照片或文件 |
| 每個欄位的出處 | 現象、原因、處置各自記錄出處：AI 推測、工程師、案件事件、問答紀錄、維修紀錄原文 | ADR-0016 |
| 審核擋下的條件 | 現象、原因、處置任一項仍是 AI 推測；現象、原因、處置、結果有空白；案件來源卻沒有相關事件 | ADR-0016 |
| 審核只提醒的條件 | 執行者空白（視為限工程師）、維修紀錄沒有事件序號、撰寫者與審核者同一人、和上一版相比沒有修改 | 使用者：同一人只提醒 |
| 維修紀錄原文 | 不必逐欄確認，審核通過就算確認 | 使用者 |
| 版本 | 每次審核通過成為新的一版，保存完整內容 | 使用者 |
| 修改已審核紀錄 | 狀態改為「修訂中」，**舊版繼續有效**，查詢顯示目前有效的版本；可以放棄修改 | 使用者 |
| 顯眼標示 | 最新一版相對於前一版改過的欄位，在查詢結果（工程師與第一線）和詳細畫面都標示「第 N 版修改」；修訂中尚未審核的變更，在詳細畫面另外標示「修改中，未審核」 | 使用者；範圍與位置由 Jev 判斷（0.92、0.79、noul 0.86） |
| 修訂經過 | 列出每一版的審核者、日期，以及每個欄位「舊 → 新」 | 使用者 |
| 停用 | 不刪除，不出現在查詢中；修訂中的修改一併放棄 | ADR-0016 |
| 恢復 | 停用的紀錄可以恢復：退回草稿，重新審核通過後成為新的一版 | 使用者 |
| 相似比對 | 分數＝相同警報代碼 ×2 ＋ 相同設備 ×1（只為了雛形，向量搜尋未模擬） | 雛形假設 |
| 工程師查詢 | 只列目前有效的版本，**不列草稿**；停用的只列編號 | 使用者 |
| 第一線查詢 | 只列目前有效的版本；執行者為「現場可執行」才顯示處置，否則顯示轉交；符合安全清單時只顯示安全清單的指示 | ADR-0014、ADR-0016 |
| 待審核清單（第 3 版） | 列出草稿與修訂中，**包含還不能審核的**；每一項顯示種類（新草稿、維修紀錄、修訂中、恢復）、開始等待的時間與等待多久、擋下的原因與提醒；可以審核的排前面，同類依等待時間由久到新；審核通過、放棄修改或停用後離開清單 | 使用者：另外做待審核清單，含還不能審核的；排序與每項顯示內容由 Jev 判斷（0.88、noul 0.66） |

## 引導情境

1. 正常流程。
2. 還有 AI 推測就審核（應被擋下；草稿不出現在查詢中）。
3. 多次修改（修訂中顯示舊版、改過的欄位標示、修訂經過）。
4. 停用後恢復。
5. 過去維修紀錄（沒有案件、沒有事件序號）。
6. 執行者與安全清單。
7. 待審核清單。

## 第 1 版試用後的結論（2026-11-13 使用者回覆）

1. 只是查詢的話，不必列出草稿。
2. 修改已審核紀錄時要看到舊版；改過多次時，把改過的地方弄得顯眼，並且要能看到所有修正的經過。
3. 停用的紀錄可以恢復（退回草稿重新審核）。
4. 維修紀錄原文審核過就算確認。
5. 撰寫者與審核者同一人：只提醒。
6. 欄位加上停機時間、處理人、照片或文件。

## 第 2 版試用後的結論（2026-11-13 使用者回覆）

- 另外做一個待審核清單，列出草稿與修訂中，包含還不能審核的。
