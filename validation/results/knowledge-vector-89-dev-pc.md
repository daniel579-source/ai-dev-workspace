## 4. 觀察（推測都是**假設**，待工程師確認）

1. **只用向量搜尋，效果不如規則關聯圖**：知識庫條目取前 1 條時召回 9～18%，取前 3 條時 36～55%；精確度都在 17% 以下。這份情境集的問題大多要看 LOG 才答得出來，例如 S08「SSCA02 停止」的正解是防火門感知器，S02「貨物沒有進來」的原因在上游設備，從問題文字的意思找不到。
2. **規則關聯圖加上向量搜尋，召回沒有增加，精確度下降**：規則關聯圖已經找到全部正解（100%），再加上向量搜尋前 1 條，精確度從 85% 降到 46～50%；加前 3 條則降到 26～27%。
3. **問題中有警報代碼時，向量搜尋反而找不到**：S01「停止 E301」、S10「停止 E302」的正解排在第 2～8 名。embedding 不擅長比對代碼，代碼應交給完全比對（ADR-0013 第 2 點）。
4. **三個模型差距很小**：各方法的召回差距都在 1～2 條以內，知識庫只有 11 條，這樣的差距不足以區分模型好壞。條目文字含不含代碼，影響也在 1 條以內。
5. **資源**：模型載入約 3～4 秒；載入後 12 個問題 105～185 ms。Ollama 回報的記憶體：e5-small 39～58 MB、bge-m3 657 MB。
6. **e5-small 的 GGUF 來源**：Hugging Face 上 cstr/multilingual-e5-small-GGUF 的檔案（原始精度與 q8_0）在本機 Ollama 0.40.16 都無法載入（`bert model needs to define token type count`）。可以載入的兩個來源，SHA-256 如下：
   - TwinSunsLLC q8_0：`e011debc1208e31bf7b6aebee2d9fc8bd2ca11694a77ed66ac9d0c9d0a877c93`
   - keisuke-miyako F16：`3c3569e72acd821a30f1c586f4d39862407da7da3f08fc7068798e5982b5f6db`
7. **限制**：
   - 這份情境集原本是為規則關聯圖設計的（`knowledge-graph-89-dev-pc.md` 第 4 節第 5 點），沒有測到向量搜尋原本要處理的情況（ADR-0015 第 5 點）：沒有警報代碼、也沒有 LOG 可以看，只是第一線的用詞和知識庫不同（例如「馬達很燙」對「馬達過熱」）。
   - 知識庫只有 11 條，與真實的數百到數千條（假設）差距很大，結果不能直接推論到真實資料。
