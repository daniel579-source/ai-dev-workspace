# 以真實樣本執行各 ADR 的後續驗證（#47 C 類，開發用電腦）

- 日期：2026-10-18
- 對應：#47 C 類「以樣本執行各 ADR 的後續驗證方式」；ADR-0003、ADR-0004、ADR-0005、ADR-0010、ADR-0011。
- 資料：本機的真實樣本（一天份，14 個檔案、19 MB、25,337 筆事件；格式紀錄見 `docs/log-format-notes.md`）。**樣本只在本機分析，本文件只記錄統計數字，不含任何 LOG 內容**（ADR-0009、CLAUDE.md 第 13 條）。
- 程式：既有的 `ImportPerformanceTests`、`SearchPerformanceTests`（`LOGTRACE_PERF_KEEP=1` 保留案件），內建預設的廠別設定；匯入後以唯讀方式查詢 `case.db` 統計，並直接讀原始檔逐筆比對。分析用的腳本只放在本機暫存區，不納入 repo。
- 電腦：與 `summary-dev-pc.md` 相同。

## 1. 與格式紀錄一致的項目

| ADR | 後續驗證方式 | 結果 |
|---|---|---|
| ADR-0003 | 全部時間戳記都能解析 | 通過：無效時間 0 筆 |
| ADR-0003、0004 | 時間倒退的筆數與統計一致，且都有標示 | 通過：PLCLOG 6 處（最大 15.7 ms）、WebServiceLOG 2 處（最大 33.8 ms），其他檔案 0；都帶「時間倒退」旗標 |
| ADR-0003 | 同時間戳記的比例與統計一致 | 通過：檔案內相鄰兩筆時間相同的比例，PLCLOG 30%、EXEDebug 42%、BCR_LOG 20% |
| ADR-0004 | 事件數與統計一致 | 通過：14 個檔案的事件數都與 `docs/log-format-notes.md` 相同；以「行首時間戳記」直接從原始檔切出的事件也是 25,337 筆 |
| ADR-0004 | DBLOG 35 筆且每筆含 stack trace | 通過：35 筆都是多行事件 |
| ADR-0004 | 編碼 | 無法解析 0 行、編碼錯誤 0 筆、未知種類 0 筆。這份樣本**沒有**私用區字元（與 #47 B 類「廠內造字」有關） |

| ADR-0010 | Big5 與 UTF-8 檔案中的同一個中文關鍵字都找得到 | 通過：同一個中文詞在 Big5 檔案 225 筆、UTF-8 檔案 41 筆都找得到 |
| ADR-0010 | 只出現在延續行的詞可以找到 | 通過：只出現在延續行的 HTTP 標頭名 157 筆、某個中文詞 7 筆，全部找得到 |

說明：

- ADR-0010 的比對對象是案件中供搜尋的正規化文字，不是畫面上的操作；搜尋本身的比對邏輯已有虛構資料的測試。`ImportPerformanceTests` 中經由搜尋 API 的兩個查詢（含某詞不含另一詞、區分大小寫）筆數也與人工比對相同。
- 「同一查詢重複執行順序相同」「重新匯入後識別碼不變」以虛構資料的測試涵蓋，這次沒有用樣本另外確認。

## 2. 案件大小超過 5 倍上限

| 項目 | 虛構資料（`search-21-dev-pc.md`） | 真實樣本 |
|---|---|---|
| 案件大小（未建全文索引） | 3.67 倍 | 4.17 倍 |
| 全文索引 | 0.23 倍 | 1.04 倍（20 MB） |
| 案件大小（含全文索引，關閉後） | 3.90 倍 | **5.22 倍**（99 MB） |

建立索引前以「當天原始 LOG × 0.3」估計索引大小（ADR-0011 第 4 點），估計後為 4.47 倍，未超過上限，所以照常建立；實際索引是 1.04 倍，估計偏低。

`SearchPerformanceTests` 在「案件 ≤ 原始 LOG 5 倍」的斷言失敗，因此同一個測試後段的「索引與掃描結果相同」「刪除索引後重建」沒有執行到。

### 各部分的大小（`case.db` 60.3 MB）

在複本上逐一刪除資料表後整理（VACUUM），看少了多少：

| 資料表 | 大小 | 內容 |
|---|---|---|
| `events` | 29.9 MB | 事件與訊息全文（訊息文字合計 17.8 MB） |
| `event_search` | 28.8 MB | 供搜尋的正規化文字（文字合計 17.8 MB） |
| `event_fields` 與其索引 | 2.1 MB | 解析欄位 |
| 其他 | < 0.3 MB | |

文字本身只有約 18 MB，兩個資料表各多出約 11 MB。

### 兩個主要原因與試算

1. **分頁大小**：`case.db` 使用 SQLite 預設的 4 KB 分頁。真實樣本有許多數 KB 的多行事件（SQL、JSON、stack trace），常常跨頁存放，浪費空間；虛構資料的事件較短，看不出這個問題。在複本上改分頁大小後整理：

   | 分頁 | `case.db` |
   |---|---|
   | 4 KB（目前） | 60.3 MB |
   | 8 KB | 44.6 MB |
   | 16 KB | 41.9 MB |
   | 64 KB | 41.0 MB |

2. **全文索引建立後留有空頁**：`index\<日期>.db` 建好後有 31% 是空頁（1,553／5,084 頁）；整理後從 19.9 MB 降到 13.8 MB。改變分頁大小則沒有差別。

兩者合計試算：原始 LOG 19.0 MB ＋ `case.db` 44.6 MB（8 KB 分頁）＋ 全文索引 13.8 MB ≈ **4.1 倍**。這只是在複本上的試算，程式沒有修改；分頁大小對搜尋與匯入速度的影響、對虛構大量資料的效果都還沒量測。

## 3. 命令串接（2026-10-18 補充，#53）

為樣本寫了 5 條命令規則（建立、派送一段、一段抵達站點、一段作業完成、命令結束），只放在本機的廠別設定（含現場系統的內部名稱，不進 repo），並在 Layout 加入樣本中的 5 台搬送機。以程式匯入樣本並推導世界狀態：

| 效果 | 筆數 |
|---|---|
| 建立命令 | 40 |
| 派送一段 | 79 |
| 一段抵達站點 | 40 |
| 一段作業完成（沒有地點，#53 新增） | 39 |
| 命令結束 | 39 |

| 命令（以命令編號串起，41 個） | 個數 |
|---|---|
| 建立 → 兩段（到站、放進儲位）→ 結束（入庫） | 33 |
| 建立 → 兩段（從儲位取貨、到站）→ 結束（出庫） | 5 |
| 建立 → 一段（到站）→ 結束 | 1 |
| 建立 → 兩段，沒有結束紀錄（標示案件範圍內未完成） | 1 |
| 只被提到，沒有建立與派送 | 1 |

- 每一段都是「派送 → 抵達或作業完成」成對出現；搬送機的命令表加入與移除各 79 筆，與派送一致。
- 「抵達回報約 40 對命令 41」：抵達回報只出現在到站的那一段；另外 1 個命令只被提到。
- 案件結束時 5 台搬送機都是閒置。
- 「命令結束」以刪除命令的紀錄判斷，取消時是否也刪除**待確認**。
